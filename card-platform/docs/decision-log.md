# Decision Log

Rule 1 requires one place for every non-trivial design choice. A choice belongs here when a competent engineer could reasonably choose another approach. Source-to-target mapping lives in the [traceability matrix](traceability-matrix.md), while open source ambiguities live in [business-rule flags](business-rule-flags.md). Code comments describe behavior and point here for rationale.

## Platform and technology selections

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **C1 — Java 25 with Spring Boot 4.1.0 for all six services** | Node.js with TypeScript; a mixed-language platform | `BigDecimal` preserves fixed-point money and permits explicit truncation. One language also keeps build and deployment behavior uniform. | Java 25 and Spring Boot 4.1 are newer than long-settled enterprise baselines. |
| **C2 — Apache Kafka in the demo, behind publishing ports** | Amazon EventBridge with SQS; direct service calls | Kafka was the requested default and preserves account-key ordering within a partition. Publishing ports keep a managed replacement possible. | The demo operates a broker container and its access-control rules. |
| **C3 — Maven mono-repo under `card-platform/`** | One repository per service | One repository makes the untouched legacy boundary auditable and keeps contracts, fixtures, services, and parity tests versioned together. | Services share a repository release cadence even though their Maven dependencies remain separate. |
| **C4 — JSON Schema Draft 2020-12 with build-enforced compatibility** | Avro with a schema registry; unchecked JSON | JSON remains readable in a console demonstration. Publish and consume validation plus compatibility tests enforce the contract without another runtime container. | A producer outside this build could ignore the compatibility gate. |
| **C5 — Representational State Transfer with JSON** | gRPC | A caller can demonstrate each synchronous route with `curl` and no generated client. | Client types are not compiled from a remote procedure contract. |
| **C6 — Exhaustive tables with short prose** | Exhaustive narrative prose | Rule 1 requires complete coverage, while Rule 5 rejects repetition. Tables carry enumeration without hiding gaps in paragraphs. | Readers who skim tables can miss a narrow exception. |
| **C7 — Simplicity governs presentation, not correctness mechanisms** | Remove the outbox, processed-event markers, or explicit mappers | The demo must remain understandable, but atomic publication and duplicate safety are required behavior. Explicit code is easier to inspect than generated code. | Each service has infrastructure tables and explicit mapping code to explain. |
| **C8 — Interest is verified but not migrated** | Build an interest service; omit interest parity | The user excluded interest migration but required interest parity. Tests verify rate lookup and arithmetic, while account cycle close reproduces only the required counter reset. | Batch interest and the event platform can evolve separately. |

## Migration strategy

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Parallel reimplementation with equivalence verification** | A strangler-fig facade routing traffic to the mainframe | The user required the services to “not call into the mainframe at runtime.” Fixtures and documented rules therefore form the executable comparison baseline. | Behavior absent from both fixtures and documented rules needs a synthetic test or remains unverified. |
| **Authorization logic is a declared synthesis** | Invent behavior for `COPAUA0C`; treat the brief’s name as an existing program | `COPAUA0C` and transaction `CP00` are absent. Rules come from `CBTRN02C`, request fields from `COTRN02C`, and the signon fork from `COSGN00C`. | There is no synchronous source program against which to compare the whole request path. |
| **Authorization reads local projections and calls no supporting service** | Synchronous account-service and card-service clients | Existing repositories, freshness fields, and tests already defined event-maintained copies. Outbound clients would add credentials and runtime coupling. | Authorization decisions can reflect projection lag. The account projection records event provenance and observation time. |
| **Only `AccountStateChanged` refreshes authorization state** | Add a `CardUpdated` consumer to authorization | `CardUpdated` carries a masked card number, while authorization indexes the full card number. Card updates cannot change cross-reference account or customer identifiers. | The seeded card cross-reference has no state-change refresh path because no in-scope mutation changes its fields. |
| **Fraud detection is marked net new** | Manufacture lineage from a nearby transaction program | No source program scores risk, checks velocity, or evaluates fraud rules. Honest traceability distinguishes design intent from migrated behavior. | Fraud tests verify the new contract, not COBOL parity. |

## Arithmetic and numeric fidelity

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Truncate every monetary result toward zero** | `RoundingMode.HALF_UP`; `RoundingMode.HALF_EVEN`; floor | `ROUNDED` appears zero times across all 28 programs in `app/cbl/`. COBOL therefore truncates stored arithmetic results. | A future “cleanup” of the rounding mode can change cents without a type error. Equivalence tests detect that change. |
| **Serialize money as a two-place decimal string** | JSON number | Common JSON clients decode numbers through binary floating point. Decimal strings preserve the fixed-point contract across languages. | Consumers must parse the value as a decimal rather than as a native floating-point number. |
| **Derive precision and scale from each Picture clause** | Store cents in integers; use one wide decimal type everywhere | `PIC S9(10)V99`, `PIC S9(09)V99`, and `PIC S9(04)V99` map to `NUMERIC(12,2)`, `NUMERIC(11,2)`, and `NUMERIC(6,2)`. | A source clause read incorrectly can propagate into entities, schemas, migrations, and tests. |
| **Keep display identifiers as fixed-width text** | Numeric identifier columns | Account, customer, merchant, and category identifiers retain leading zeros and are compared as display fields. | Text storage does not provide numeric ordering, which these identifiers do not need. |
| **Reproduce tolerant numeric input parsing** | `new BigDecimal(String)` | `FUNCTION NUMVAL-C` accepts separators and currency notation at `app/cbl/COTRN02C.cbl:L383`; `app/cbl/COACTUPC.cbl:L2201` gates the same conversion. | Inputs rejected by stricter systems remain acceptable for parity. |

## Data model and persistence

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Use `DATE` for card expiry and `VARCHAR(10)` for account expiry** | Use one date type for both fields | Card expiry is decomposed into calendar parts at `app/cbl/COCRDUPC.cbl:L115-L123`. Account expiry is compared as text at `app/cbl/CBTRN02C.cbl:L414`. | Similar business terms have different database types, so a later unification could break parity. |
| **Drop trailing filler bytes** | Persist filler columns | The account, customer, transaction, cross-reference, category-balance, and card fillers carry no business data. The [traceability matrix](traceability-matrix.md) records every omission. | Fixed-width loaders must still account for bytes that no database column stores. |
| **Adopt `CVCUS01Y.cpy` as the canonical customer layout** | Adopt `CUSTREC.cpy`; merge the two copies | Four programs bind to `CVCUS01Y`; `app/cbl/CBSTM03A.CBL:L55` binds to the fork. The copies differ in one field name. | Code that depended on the fork’s identifier spelling now follows the canonical name. |
| **Correct `EXPIRAION` in target field and column names** | Preserve the source misspelling | Identifier text does not affect behavior. The mapping records both renames for source searches. | A direct search for the corrected target name finds no source identifier. |
| **One private database and schema per service** | A shared schema; cross-schema reads | Private ownership enforces service boundaries. A service needing foreign state holds a projection or seeded reference copy. | Replicas and repeated reference rows can lag or drift. |
| **Store the fraud velocity window in PostgreSQL** | Redis; in-memory state | PostgreSQL avoids another demo container and preserves state across restarts. The repository boundary permits a later replacement. | Database reads and writes cost more than an in-memory cache at high volume. |
| **Seed small reference lookups into each owning schema** | Shared lookup tables; a seventh service | Seven transaction types and 18 categories are cheaper to duplicate than to fetch over the network. | Repeated seed data must change consistently. |
| **Persist the card verification value but never emit it** | Drop the source field; expose it with the card record | `app/cpy/CVACT02Y.cpy:L7` defines the field, so storage preserves the layout. Entities, responses, events, and logs expose no accessor or value. | The sensitive value still exists in the card service database. |
| **Use encoded HTTP Basic passwords instead of the source plaintext comparison** | Reproduce the direct comparison at `app/cbl/COSGN00C.cbl:L223` | Every service already applies the same default-deny security chain. | **Notification owns an account-keyed cardholder projection** | Blank renderer context; synchronous account lookup; a shared customer table | Both notification consumers need stable cardholder context and cannot call another consumer. | **Authorization unresolved-card attempts have their own table** | Discard the failed request; force a false account identifier | Reason 0100 has no resolved account. A transaction-keyed attempt row preserves the input and supports one-event-per-call without inventing an account. | Authorization’s outbox accepts two aggregate-key forms and must distinguish them by width. |

## Event contracts and messaging

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Use a transactional outbox in each producing service** | Publish inside request handling; distributed database-broker transactions | The source performs three writes without rollback at `app/cbl/CBTRN02C.cbl:L440-L442`. Domain state and the event row now commit together. | Publication occurs after the domain transaction and can be delayed until the relay succeeds. |
| **Use a processed-event marker inside the consumer transaction** | In-memory deduplication; rely on broker delivery alone | A replay reaches the source duplicate-key abend path at `app/cbl/CBTRN02C.cbl:L562-L579`. Durable markers survive restarts and guard side effects. | Marker tables require retention rules that remain longer than ordinary topic replay windows. |
| **Use account identifier as the Kafka key when known** | Random key; transaction identifier | The ledger must preserve per-account order. Kafka orders records within a partition. | One unusually active account concentrates work on one partition. |
| **Use a transaction key for unresolved-card declines** | Omit the event; invent an account identifier | Transformation rule T4 requires one event per authorization call. A 16-character transaction key is truthful when the card cannot resolve an account. | Consumers must accept either an 11-digit account key or the sanctioned transaction key. |
| **Publish `TransactionPosted` schema version 2 with statement detail** | Pad nine columns in notification; break version 1 | Ledger already receives the authoritative fields on `TransactionAuthorized`. An additive version carries them forward while version 1 remains readable. | Consumers that require statement detail must reject version 1 rather than invent values. |
| **Share `fraud.assessed` between `FraudFlagged` and `FraudCleared`** | One topic per verdict | The envelope’s `eventType` discriminates the payload, and one topic keeps the demo routing surface smaller. | A listener interested in one verdict still reads both event types. |
| **Receive `fraud.assessed` as `Object` before type discrimination** | A `FraudFlagged`-typed listener | `FraudCleared` is structurally narrower. Typed conversion could fail before application code recognizes a valid cleared event. | The listener must reject every object outside the two governed record types. |
| **Mask the card number only at publication and response boundaries** | Mask before authorization; emit the full number | Authorization needs the full 16-character key. Payloads and logs need only the masked value. | The full card number remains in memory and in owning-service tables. |
| **Emit currency as constant `USD`** | Omit currency; infer it in every consumer | The required event field has no source equivalent, and the source system is United States only. | Supporting another currency requires a contract and domain change. |
| **Treat reason 109 as an observable infrastructure failure** | Reproduce the source’s unread reason code | The source sets reason 109 at `app/cbl/CBTRN02C.cbl:L556` after a write and never checks it. The target retries, then dead-letters. | A condition the source swallowed now becomes operationally visible. |
| **Replace the single abend path with typed outcomes** | One fatal error path | Expected declines return HTTP 200 with `approved=false` and publish an event. Infrastructure failures retry, and terminal failures produce governed dead-letter metadata. | More outcome paths require separate tests and monitoring. |
| **Publish supporting-service events only after state changes** | Publish read events; publish nothing | The user limited supporting services to mutation events. Account updates and cycle close publish `AccountStateChanged`; customer changes publish `CustomerContextChanged`; card updates publish `CardUpdated`. | Authorization and notification depend on their local projections staying within the configured freshness bounds. |
| **Govern eight business event types and one dead-letter envelope** | Limit schemas to the five initial core events | The delivered platform also publishes account, customer-context, and card state changes, as required for supporting-service mutations and notification projection freshness. All runtime wire forms use the same validation gate. | The contract library governs service-owned records that it does not bind to Java classes itself. |

## Defects reproduced rather than fixed

Equivalence is the acceptance contract. The target reproduces the following outcomes and exposes each issue for human review rather than silently changing it.

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Reproduce the credit-limit precision narrowing** | Widen the temporary value | `WS-TEMP-BAL` is `PIC S9(09)V99` at `app/cbl/CBTRN02C.cbl:L187`, while the limit and accumulators use `S9(10)V99` at `app/cpy/CVACT01Y.cpy:L8` and `L13-L14`. | A very large cycle balance can lose its high-order digit and turn a decline into approval. |
| **Reproduce the refund sign convention** | Treat a refund as reducing cycle debit | The source adds a negative amount to cycle debit at `app/cbl/CBTRN02C.cbl:L551`, then subtracts that accumulator at line 404. | A refund tightens the next authorization instead of restoring credit. |
| **Reproduce the overlimit formula without current balance** | Include `ACCT-CURR-BAL` | `app/cbl/CBTRN02C.cbl:L403-L407` uses only cycle credit, cycle debit, and the incoming amount. | Stated balance and tested available credit can disagree. |
| **Preserve the message-2513 date tolerance** | Accept only severity zero | `app/cbl/COTRN02C.cbl:L397-L400` accepts one undocumented validator message as well as ordinary success. | The tolerated condition may be a source defect rather than intended policy. |
| **Preserve processing timestamps at hundredths** | Emit full Java fractional precision | `app/cbl/CBTRN02C.cbl:L173-L174` stores two significant fractional digits and line 701 fills four zeros. | Raw byte comparison needs the documented normalization. |
| **Reject impossible calendar dates at the card database boundary** | Preserve every ten-character source date | PostgreSQL `DATE` cannot store a text such as `2028-02-31`. ## Validations deliberately not added

Adding any rule below would change authorization results and break the required source parity.

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **No Luhn or checksum validation** | Validate the card-number checksum | `app/cbl/COCRDUPC.cbl:L194` checks only 16 numeric digits. | A checksum-invalid card can pass the same structural rule as the source. |
| **No card-status authorization check** | Reject inactive cards | `CBTRN02C` never opens the card file, and `POSTTRAN.jcl` never allocates it. | An inactive card can authorize if every implemented source rule passes. |
| **No account-status authorization check** | Reject inactive accounts | `ACCT-ACTIVE-STATUS` exists at `app/cpy/CVACT01Y.cpy:L6` but is not tested before posting. | A closed account can authorize under source-equivalent rules. |

## Runtime, configuration and infrastructure decisions

### Platform and runtime wiring

| Decision | Alternatives considered | Why | Risks accepted |
|---|---|---|---|
| Publish the event through a transactional outbox rather than from the request handler | Publish directly after the write; publish inside a distributed transaction across the database and the broker | The decision row and the event row commit in one local transaction, so a decision can never exist without its event or an event without its decision. The source has an ancestor for the shape: `app/cbl/CORPT00C.cbl:L517-L518` writes to a queue and lets a separate reader pick the work up. It also has the gap: `app/cbl/CBTRN02C.cbl:L440-L442` performs three writes with no rollback, and every file in `app/csd/CARDDEMO.CSD:L3-L9` declares `RECOVERY(NONE) JOURNAL(NO)` | An event is published after the commit rather than with it, so a consumer sees it late rather than never. Two writes per call instead of one |
| All five producer services use one claimed-row relay state machine | Let each relay poll unlocked rows; rely on one replica; keep the older pessimistic-lock query without durable claim state | A rolling deployment or manual scale-out can run two relay instances over one table. `FOR UPDATE SKIP LOCKED` gives each transaction a disjoint due batch, `claimed_by` and `claimed_at` make the winner durable, and the claim timeout recovers work from an instance that stopped. The attempt count, due time and bounded backoff prevent one refused row from being retried on every sweep. One explicit `TransactionTemplate` boundary also keeps counters and timers outside the database transaction, so a rollback cannot report success | A broker round trip holds a database transaction and row locks. A send that succeeds before the database commit fails can be repeated, so consumers still need processed-event idempotency |
| Every service applies one bounded `service` common tag to application and framework meters | Tag only hand-written meters; rely on scrape-target labels; leave services inconsistent | One collector receives application, Java Virtual Machine, HTTP, and database meters from all six services. A registry customizer applies the same dimension before any meter is registered, so every series can be grouped with one query and no service-specific exception | The service name is present both in the metric prefix and as a tag on hand-written series. The duplication is bounded to six values |
| Readiness checks the database, Kafka, expected listener containers and terminal outbox state, while liveness checks process state alone | Keep Boot's generated `readinessState` group; put external dependencies in liveness; probe the aggregate health endpoint | A process can stay alive after its database or broker is lost, a listener is stopped, or a relay abandons an event. Those states cannot serve the platform contract and must withdraw the instance without restarting a healthy Java virtual machine. Database acquisition and Kafka discovery have explicit short deadlines, and Compose and Kubernetes probe the same readiness group | A transient shared dependency outage can withdraw every replica at once. An abandoned outbox row keeps a producer unready until an operator resolves it; that is deliberate because later events must not overtake the failed row |
| Compose reads `.env` for interpolation but every application container receives an explicit environment map | Attach `.env` to every service with `env_file`; split one dotenv file per service; put all credentials in the shared environment anchor | Compose interpolation can select one service's database and broker credentials without injecting the source variables themselves. Removing `env_file` prevents the PostgreSQL superuser, Kafka administrator and five sibling service credentials from entering each application container, while one checked-in map keeps the demo runnable from a single operator file | The six service blocks repeat their own settings, and adding a new application property requires adding it to the owning block. A build contract checks the active relay, consumer and retention keys so an omission fails before deployment |
| Dotenv bcrypt values are single quoted | Leave generated hashes unquoted; escape every dollar sign as `$$` | A generated bcrypt value contains several dollar signs. Compose expands dollar-prefixed text in unquoted and double-quoted dotenv values, corrupting a valid hash before Spring Security reads it. Single quotes preserve the generated value character for character and are easier to paste correctly than escaping each dollar sign | The quotes must remain around the replacement value. The example and a Compose runtime check demonstrate that requirement |
| Kubernetes stores the single demo broker's KRaft log, topic records and committed offsets on a `ReadWriteOnce` persistent claim | Keep `emptyDir`; rebuild broker state on every Pod replacement; require an external managed broker | A Deployment replacement is routine maintenance, not an instruction to erase every topic and every consumer position. A claim also keeps the configured KRaft cluster identifier paired with the metadata it names. The standard-cluster manifest remains self-contained and uses the cluster's default storage class | The 2 GiB claim is single-node demo storage, not a highly available broker design. A cluster without a default storage class leaves the claim pending, and deleting the claim remains the explicit destructive reset |
| Each service mounts its own server keystore while all services share one trust-only Secret | Mount one shared keystore in all six Pods; duplicate the same truststore into six Secrets; terminate Transport Layer Security outside the services | The six Services have different Domain Name System names, so each certificate must identify its own endpoint and each private key must stay within that workload's boundary. The certificate authority and truststore are public trust material rather than service identity, so one trust-only Secret avoids six copies without sharing a private key | Operators must issue and rotate six certificates and six keystore passwords. The checked-in Secret file contains placeholders only and must be replaced before deployment |
| Kubernetes uses `imagePullPolicy: Never` for the six locally built demo images | `IfNotPresent`; `Always`; require a registry before the demo can run | The repository defines local Docker builds and no image registry. `Never` makes that contract explicit: a node either has the exact image the operator built or the Pod fails, instead of silently pulling a same-named image from a default registry or running a stale cached tag | Every node that can schedule a service must have the image preloaded. A multi-node or remote cluster needs a registry and a deliberate pull-policy change |
| Every service image tag in Kubernetes is the Maven project version | Keep the stale `1.0.0` literal; use `latest`; version the deployment independently | The build produces `1.0.0-SNAPSHOT`, so a manifest naming `1.0.0` asks Kubernetes for an artifact this reactor did not build. Deriving the tag from `project.version` keeps the build command, the six manifests and the deployment contract on one version | A snapshot tag is mutable and is suitable only for this demo. A production release should publish immutable versioned images, preferably with a digest |
| Producer services enforce outbox and processed-marker retention with scheduled, explicit transactions | Keep the settings as documentation only; remove the settings; run one platform-wide database job | A configured horizon with no caller is false configuration. Each service owns its schema, so each service deletes only its own published rows and markers. Two explicit `TransactionTemplate` calls avoid the self-invocation trap that would leave modifying queries outside a transaction | Five small scheduled components repeat the same shape. A failed sweep delays deletion until the next interval but never blocks business traffic |
| Every consumer records processed event identifiers | Rely on broker exactly-once semantics; deduplicate in memory | Kafka delivers at least once, and a rebalance or a restart mid-batch redelivers. The source has no duplicate detection at all: a replayed feed drives the transaction write at `app/cbl/CBTRN02C.cbl:L562-L579` into a duplicate key and straight to the abend routine. An in-memory guard loses its contents on the restart that causes the redelivery | One extra table and one extra read per delivery. The marker table grows and needs a retention horizon |
| Money is a decimal string on the wire, never a JSON number | JSON number; integer minor units | Most readers deserialize a JSON number into a binary floating-point double, which reintroduces the representation this platform exists to avoid. A string with a two-decimal pattern in the schema cannot be widened into a double by accident | Consumers must parse rather than read a number directly |
| All monetary arithmetic truncates toward zero | `HALF_UP`; `HALF_EVEN` | The `ROUNDED` phrase appears zero times across all twenty-eight programs in `app/cbl/`, so every arithmetic store in the source truncates. `HALF_UP` is the reflexive choice in Java and it breaks equivalence by one cent, silently | A reader unfamiliar with the source will find `RoundingMode.DOWN` surprising, which is why one test asserts that half-up rounding produces a different answer |
| The account identifier is the Kafka message key on every event | Transaction identifier; no key | Kafka guarantees order within a partition only. The ledger's balance updates for one account must not be reordered, and keying on the account is what keeps them on one partition | One hot account concentrates on one partition |

### Authorization service

| Decision | Alternatives considered | Why | Risks accepted |
|---|---|---|---|
| Keep `card_xref` and `account_credit_snapshot` current by consuming `account.state-changed` and `card.updated`, rather than calling the account and card services synchronously per authorization | Synchronous REST reads on the authorization path; a shared database; no replication at all | The plan states that `account_credit_snapshot` is kept current by account events, and replication keeps the response path free of two network calls that would each be able to fail or hang. A synchronous read would put two more services in the blast radius of every authorization | The replica can lag. That risk is what `carddemo.replica.max-staleness` and the refusal below exist to bound. Two more consumer groups to operate |
| Refuse an authorization whose replica rows are older than `carddemo.replica.max-staleness`, as an infrastructure fault | Decline the transaction; approve anyway and log; add a fifth reject reason | A stale replica fails silently, which is what makes it dangerous: the credit-limit rule at `app/cbl/CBTRN02C.cbl:L403-L407` computes an answer from obsolete numbers and approves what the current numbers would decline. A fifth reject reason was rejected outright: `app/cbl/CBTRN02C.cbl:L385-L420` defines exactly four, `DeclineReason` holds exactly those four and the published schema enumerates them, so a fifth value breaks every consumer. It would also be untrue — the card and the account did nothing wrong, this service is the component unable to answer | A replica that stops being fed refuses traffic instead of serving it. That is the intended trade: refusing is visible, and approving against unknown numbers is not |
| Default `carddemo.replica.max-staleness` to one day | Minutes; seconds | The demo runs for its whole length with no account or card mutation, so a short window would refuse every transaction after a few minutes and an operator would read the control working as a broken demo | A day is far too long for a deployment receiving real state-change traffic, which is why the configuration comment says to shorten it |
| Bind the two consumed events to authorization-local records rather than importing the producer's class | Import `com.carddemo.account.messaging.AccountStateChanged`; promote both records into `libs/event-contracts` | No service module may depend on another, so the import would not compile — that restriction is the mechanism that makes "no synchronous coupling between consumers" a build-verified property rather than a review comment. `libs/event-contracts` deliberately holds the schema document for these two events and names no class to build, because the record belongs to the service owning the aggregate. The shared JSON Schema is the contract, and the deserializer validates every message against it | Two small records describe the same payload in two modules. The schema is what keeps them in step, and a divergence fails validation rather than passing silently |
| A `CardUpdated` message refreshes the observation on `card_xref` and writes no mapping field | Upsert the row; match on the last four digits and rewrite `account_id`; consume nothing | The message carries a masked card number because no full card number travels on any topic. `card_xref` is keyed by the full sixteen characters, so the message cannot name a key: it can neither create a row nor safely move a mapping. It does carry the account identifier, so it does confirm the owning service just wrote that account's card data, which is what the observation column records | Where two cards of one account share their last four digits, both rows are refreshed and one of them was not the card the event named. Bounded and safe: both already name this account and no mapping value changes, so no authorization can be misrouted |
| Record every metric of a decision outside the transaction that commits it | Annotate the method `@Transactional` and count inside it; count inside and compensate on rollback | A meter takes no part in a database transaction, so an increment inside one survives the rollback that discards the decision. The approval count would then exceed the events the outbox holds, and the difference would be invisible. The timer is described as running to commit, and a sample stopped inside the transaction excludes the flush and the commit, which is where a slow decision spends its time | The transaction boundary is an explicit `TransactionTemplate` call rather than an annotation, which is one more line and no proxy subtlety |
| Serialize published events with the string serializer, not `JsonSchemaValidatingSerializer` | Name the validating serializer on the producer | The value reaching the template is already the JSON text stored in `outbox_event.payload`, and it was validated against its schema at write time inside `OutboxWriter`, where a rejected event can still roll back its own transaction. The validating serializer writes one of the registered event *records* and refuses every other value, so it would refuse this text outright: every publish would raise a serialization exception, the outbox would retry for ever, and the service would look healthy throughout | The producer performs no validation. The write-time gate is the one that matters, because it is the only one that can still roll back |
| One schema name for the datasource URL, Flyway and Hibernate, all defaulting to `authorization_service` | Leave the Hibernate default at `authorization`, since deployments set the shared variable anyway | Flyway migrated one schema while Hibernate validated another, and a deployment that set `AUTHORIZATION_DB_SCHEMA` made the two agree and hid it completely. The failure therefore appeared only when the service ran on its defaults, which is exactly what onboarding asks a new developer to do first | None. The values were already meant to be the same |
| Route a replica record that can never be applied to the dead-letter topic after bounded retries | Retry for ever; drop it; stop the container | A record whose bytes break the schema breaks it on every attempt, so retrying only stalls the partition behind it. Dropping it loses the evidence. The dead letter carries the four diagnostic fields of `01 ABEND-DATA` at `app/cpy/CSMSG02Y.cpy:L21-L29` and no payload value, because the record may hold a credit limit or a pair of cycle balances | The replica misses that one change until an operator replays it |

### Notification service

| Decision | Alternatives considered | Why | Risks accepted |
|---|---|---|---|
| Acknowledge a rolled-back delivery only when a committed processed-event marker proves the work was already done | Treat every integrity violation as a concurrent duplicate and acknowledge | `statement_transaction` and `notification_log` raise the same exception type on a constraint of their own, and acknowledging those would discard the event silently. Re-reading the marker after the rollback establishes which collision it was rather than assuming | One extra read on the failure path |
| Count failed attempts and dead-lettered records on two separate series | One counter for both | One record retried three times and then dead-lettered incremented a single counter four times, while a record refused at deserialization incremented it once. The number answered no question. `failures` now counts one attempt and `records.dead.lettered` counts one record | Two series to read instead of one |
| Register no `TransactionAuthorized` metric series in this service | Keep the series for symmetry with the other consumers | This service consumes `transaction.posted` and `fraud.assessed`, which is exactly what its broker entries grant it. A series that can only ever read zero states something about the topology that is not true | The six services' meter sets are not identical, which is correct: their topologies are not identical either |
| Enforce the shipped retention horizons with a scheduled sweep | Leave the horizons documented and unapplied; drop the settings | Three tables grow by one row per consumed event and nothing else removed a row, so every horizon in `application.yml` and in the `COMMENT ON TABLE` statements was a claim about intent rather than behaviour. A horizon nothing enforces is worse than none: a reader takes the table for bounded and it is not | A scheduled deletion runs against financial records. Each sweep is bounded by an index and runs in its own transaction, and a failure is logged and retried on the next pass rather than failing a delivery |
| Open each retention delete's transaction explicitly rather than annotating the three sweep methods | `@Transactional` on each method, called from the scheduled method | The scheduled method reaches its neighbours on `this`, which does not pass through the proxy that would start the transaction, and a modifying query outside a transaction fails. That failure arrives as a data-access exception, which the sweep logs and swallows, so the annotation would have left every horizon unenforced while reporting nothing louder than a warning | None. The explicit boundary cannot be bypassed that way, and one test counts the transactions opened |
| The `processed_event` retention window is stated once, in `application.yml`, and the table comment points at it | Restate the number in the `COMMENT ON TABLE` text | The comment said thirty days while the setting shipped one hundred and sixty-eight hours. Two numbers for one policy drift, and the one an operator reads is not the one the sweep applies | An operator reading the catalogue must follow one reference to get the value |

### Fraud detection service

This service has no COBOL ancestor. Searching `app/cbl/` for `fraud`, `velocit`, `risk` and `scoring` matches none of its 28 programs, so every value below was chosen rather than derived, and each row says so.

| Decision | Alternatives considered | Why | Risks accepted |
|---|---|---|---|
| A rule that triggers does not by itself flag; the summed score is compared against `carddemo.fraud.risk.flag-threshold` | Treat any triggered rule as a flag and delete the threshold; keep both and let the threshold stay unread | The threshold was bound and validated and then never read, so a single 25- or 30-point rule published `FraudFlagged` while the shipped configuration said 50. Two readings of the same file disagreed. A threshold is also the only way a score means anything: without one, the score is decoration and every rule is equally final | A single rule now clears. That is the intended reading of a threshold of 50 against rules worth 30, 30 and 25, and the score and the rules that objected are still recorded on the row |
| The threshold travels inside `RiskAssessment` and `flagged()` derives from it | Store a computed boolean; pass the threshold to each caller | A stored verdict can contradict the score beside it, and a threshold passed around is a policy in several places. Deriving from the two values it depends on makes disagreement unrepresentable | The record carries one more component, so its construction sites all name the threshold |
| `flag-threshold` starts at 1, not 0 | Keep `@Min(0)` | Zero flags a transaction no rule objected to, and `fraud-flagged-v1.json` requires a flagged event to name at least one rule, so zero would produce an event the contract refuses and a row the schema refuses. Rejecting it at start-up names the property; accepting it fails later, per message | A configuration that set 0 now fails to start. No shipped file sets it |
| `fraud_assessment` refuses a flag with no rule, and permits rules without a flag | Keep the constraint as a biconditional; drop the constraint | The biconditional made a below-threshold row unstorable, so applying the threshold would have failed at the database. The remaining half is still worth enforcing: every rule scores above zero and the threshold is at least one, so a score that reached it must name a rule, and a flagged row naming none states a conclusion with no reason behind it | `flagged` alone no longer tells a reader whether a rule triggered. `triggered_rules` does, and it is on the same row |
| Count deserialization and schema failures in the recoverer, not in the listener | Count them in the listener; count every recovered record there | `ErrorHandlingDeserializer` records the failure and the container raises it before any listener is invoked, so the listener line that counted it could never run. The recoverer is the only place that sees one. Counting *every* recovered record there instead would double-count a business failure, which the listener already counts once per attempt | The two counts must stay disjoint. They are, because a payload that did not read never reached a listener |
| Register a dead-letter topic override on the validating serializer | Send dead letters through a second plain template; stop validating on publish | The relay sends its `DeadLetterEnvelope` through the same template as the two assessment events, and the validating serializer refuses an event whose type is not bound to the topic it was sent to. It knows only the default name, so any deployment that renamed the dead-letter topic had every dead letter refused — and the row that could not be published became unpublishable too, retried by every sweep, failing identically for as long as the service ran | Three event types now share one factory, so a fourth destination needs a fourth override. The build asserts it |
| Fraud validates on publish while the other services publish text | Publish text here as well | This relay reads the outbox payload back into the event record before sending, so it hands the template a record and the validating serializer can check it. The other relays hand over the stored JSON text unchanged, which that serializer refuses by design, and their publish-side gate runs at write time instead | Two publish shapes exist across the platform. Each service's producer configuration states which one it uses |
| The four risk values are demonstration values | Derive them from the fixtures; omit them | No measurement stands behind any of them, and `app/data/ASCII/dailytran.txt` carries no fraud outcome to fit against. Naming them as chosen is honest; deriving a threshold from data that contains no labels would not be | The numbers are illustrative. `docs/business-rule-flags.md` is where a reader is told which platform values are measured and which are chosen |
