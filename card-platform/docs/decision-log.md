# Decision Log

Rule 1 requires one place for every non-trivial design choice. A choice belongs here when a competent engineer could reasonably choose another approach. Source-to-target mapping lives in the [traceability matrix](traceability-matrix.md), while open source ambiguities live in [business-rule flags](business-rule-flags.md). Code comments describe behavior and point here for rationale.

## Platform and technology selections

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **C1 — Java 25 with Spring Boot 4.1.0 for all six services** | Node.js with TypeScript; a mixed-language platform | `BigDecimal` preserves fixed-point money and permits explicit truncation. One language also keeps build and deployment behavior uniform. | Java 25 and Spring Boot 4.1 are newer than long-settled enterprise baselines. |
| **C2 — Apache Kafka in the demo, behind publishing ports** | Amazon EventBridge with SQS; direct service calls | Kafka was the requested default and preserves account-key ordering within a partition. Publishing ports keep a managed replacement possible. | The demo operates a broker container and its access-control rules. |
| **C3 — Maven mono-repo under `card-platform/`** | One repository per service | One repository makes the untouched legacy boundary auditable and keeps contracts, fixtures, services, and parity tests versioned together. | Services share a repository release cadence even though their Maven dependencies remain separate. |
| **C4 — JSON Schema Draft 2020-12 with build-enforced compatibility** | Avro with a schema registry; unchecked JSON | JSON remains readable in a console demonstration. Publish and consume validation plus compatibility tests enforce the contract without another runtime container. | A producer outside this build could ignore the compatibility gate. |
| **C5 — Representational State Transfer with JSON** | gRPC | A caller can demonstrate each synchronous route with `curl` and no generated client. | Client types are not compiled from a remote procedure contract. |
| **C6 — Exhaustive tables with short prose** | Exhaustive narrative prose | Rule 1 requires complete coverage, while Rule 5 rejects repetition. Tables carry enumeration without hiding gaps in paragraphs. | Readers who skim tables can miss a narrow exception. |
| **C7 — Simplicity governs presentation, not correctness mechanisms** | Remove the outbox, processed-event markers, or explicit mappers | The demo must remain understandable, but atomic publication and duplicate safety are required behavior. Explicit code is easier to inspect than generated code. | Each service has infrastructure tables and explicit mapping code to explain. |
| **C8 — Interest is verified but not migrated** | Build an interest service; omit interest parity | The user excluded interest migration but required interest parity. Tests verify rate lookup and arithmetic, while account cycle close reproduces only the required counter reset. | Batch interest and the event platform can evolve separately. |

## Migration strategy

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Parallel reimplementation with equivalence verification** | A strangler-fig facade routing traffic to the mainframe | The user required the services to “not call into the mainframe at runtime.” Fixtures and documented rules therefore form the executable comparison baseline. | Behavior absent from both fixtures and documented rules needs a synthetic test or remains unverified. The precision boundary is the concrete instance: no cycle balance in the 300-record daily fixture reaches one billion, so a constructed case carries that proof. |
| **Authorization logic is a declared synthesis** | Invent behavior for `COPAUA0C`; treat the brief’s name as an existing program | `COPAUA0C` and transaction `CP00` are absent. Rules come from `CBTRN02C`, request fields from `COTRN02C`, and the signon fork from `COSGN00C`. | There is no synchronous source program against which to compare the whole request path. |
| **Authorization reads local projections and calls no supporting service** | Synchronous account-service and card-service clients | Existing repositories, freshness fields, and tests already defined event-maintained copies. Outbound clients would add credentials and runtime coupling. | Authorization decisions can reflect projection lag. The account projection records event provenance and observation time. |
| **Two events refresh authorization state, and `CardUpdated` refreshes an observation rather than a mapping** | Consume only `AccountStateChanged`; upsert `card_xref` from `CardUpdated`; call the card service synchronously | Authorization consumes both streams. `AccountStateChanged` replaces every value column of `account_credit_snapshot`, because a decision reads all of them. `CardUpdated` cannot do the same for `card_xref`: it carries a masked card number, while that table is keyed by the full sixteen characters. The message can therefore neither create a row nor move a mapping. It does name the account whose card data was just written, so it refreshes the observation column and nothing else. The per-consumer detail is in [Authorization service](#authorization-service). | Where two cards of one account share their last four digits, both rows are refreshed and one of them was not the card the event named. Bounded and safe: both already name that account and no mapping value changes. |
| **Fraud detection is marked net new** | Manufacture lineage from a nearby transaction program | No source program scores risk, checks velocity, or evaluates fraud rules. Honest traceability distinguishes design intent from migrated behavior. | Fraud tests verify the new contract, not COBOL parity. |

## Arithmetic and numeric fidelity

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Truncate every monetary result toward zero** | `RoundingMode.HALF_UP`; `RoundingMode.HALF_EVEN`; floor | `ROUNDED` appears zero times across all 28 programs in `app/cbl/`. COBOL therefore truncates stored arithmetic results. | A future “cleanup” of the rounding mode can change cents without a type error. Equivalence tests detect that change. |
| **Serialize money as a two-place decimal string** | JSON number | Common JSON clients decode numbers through binary floating point. Decimal strings preserve the fixed-point contract across languages. | Consumers must parse the value as a decimal rather than as a native floating-point number. |
| **Derive precision and scale from each Picture clause** | Store cents in integers; use one wide decimal type everywhere | `PIC S9(10)V99`, `PIC S9(09)V99`, and `PIC S9(04)V99` map to `NUMERIC(12,2)`, `NUMERIC(11,2)`, and `NUMERIC(6,2)`. | A source clause read incorrectly can propagate into entities, schemas, migrations, and tests. |
| **Keep display identifiers as fixed-width text** | Numeric identifier columns | Account, customer, merchant, and category identifiers retain leading zeros and are compared as display fields. | Text storage does not provide numeric ordering, which these identifiers do not need. |
| **Reproduce tolerant numeric input parsing** | `new BigDecimal(String)` | `FUNCTION NUMVAL-C` accepts separators and currency notation at `app/cbl/COTRN02C.cbl:L383`; `app/cbl/COACTUPC.cbl:L2201` gates the same conversion. | Inputs rejected by stricter systems remain acceptable for parity. |

## Event contracts and messaging

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Use a transactional outbox in each producing service** | Publish inside request handling; distributed database-broker transactions | The source performs three writes without rollback at `app/cbl/CBTRN02C.cbl:L440-L442`. Domain state and the event row now commit together. | Publication occurs after the domain transaction and can be delayed until the relay succeeds. |
| **Use a processed-event marker inside the consumer transaction** | In-memory deduplication; rely on broker delivery alone | A replay reaches the source duplicate-key abend path at `app/cbl/CBTRN02C.cbl:L562-L579`. Durable markers survive restarts and guard side effects. | Marker tables require retention rules that remain longer than ordinary topic replay windows. |
| **Use account identifier as the Kafka key when known** | Random key; transaction identifier | The ledger must preserve per-account order. Kafka orders records within a partition. | One unusually active account concentrates work on one partition. |
| **Use a transaction key for unresolved-card declines** | Omit the event; invent an account identifier | Transformation rule T4 requires one event per authorization call. A 16-character transaction key is truthful when the card cannot resolve an account. | Consumers must accept either an 11-digit account key or the sanctioned transaction key. |
| **Publish `TransactionPosted` schema version 2 with statement detail** | Pad nine columns in notification; break version 1 | Ledger already receives the authoritative fields on `TransactionAuthorized`. An additive version carries them forward while version 1 remains readable. | Consumers that require statement detail must reject version 1 rather than invent values. |
| **Share `fraud.assessed` between `FraudFlagged` and `FraudCleared`** | One topic per verdict | The envelope’s `eventType` discriminates the payload, and one topic keeps the demo routing surface smaller. | A listener interested in one verdict still reads both event types. |
| **Receive `fraud.assessed` as `Object` before type discrimination** | A `FraudFlagged`-typed listener | `FraudCleared` is structurally narrower. Typed conversion could fail before application code recognizes a valid cleared event. | The listener must reject every object outside the two governed record types. |
| **Mask the card number only at publication and response boundaries** | Mask before authorization; emit the full number | Authorization needs the full 16-character key. Payloads and logs need only the masked value. | The full card number remains in memory and in owning-service tables. |
| **Derive card identity as a keyed, versioned code rather than a plain digest** | An unkeyed SHA-256 digest of a labelled card number; a random surrogate issued by a vault | A card number is sixteen digits, so anyone holding a token can recompute an unkeyed digest for every candidate. This platform puts tokens in routes, cursors, responses and authorities. `HmacSHA256` under a deployment key removes that search, and folding the version into the covered message makes a rollover a configuration change rather than a code change. A vault surrogate needs a service the user excluded from a demo, and AAP section 0.2.2 excludes payment-card industry controls beyond the documented masking deviation. | The key is deployment state that has to reach every service, and turning it over re-derives every stored token and granted authority. `CardTokenKeyContractTest` holds the four artifacts that carry one to a single key and version, and `docs/suggested-next-tasks.md` carries the turnover procedure. |
| **Supply no default card-token key, and refuse to derive a token without one** | Compile a demo key into the helper; fall back to an unkeyed digest when no key is set | A key compiled into the repository is a key every reader holds, which is the property the key exists to remove. A silent fallback is worse, because the weaker derivation would be invisible. A refusal names the property that supplies the key. | Every runtime path and every test run has to be given the key. `pom.xml` supplies it to Surefire and Failsafe, and the Compose stack, the ConfigMap and the Secret template supply it at run time. |
| **Report a card token as present or withheld in a log rendering, never in full** | Log the token; log a prefix of it | The token discloses no card number, but it names one card for as long as its key stands. A log line carrying it lets any reader of that log follow the card across every request that touched it. A prefix of a keyed code is equally linkable. | An operator diagnosing a paging or read-model problem locates a row by transaction identifier rather than by card. |
| **Emit currency as constant `USD`** | Omit currency; infer it in every consumer | The required event field has no source equivalent, and the source system is United States only. | Supporting another currency requires a contract and domain change. |
| **Treat reason 109 as an observable infrastructure failure** | Reproduce the source’s unread reason code | The source sets reason 109 at `app/cbl/CBTRN02C.cbl:L556` after a write and never checks it. The target retries, then dead-letters. | A condition the source swallowed now becomes operationally visible. |
| **Replace the single abend path with typed outcomes** | One fatal error path | Expected declines return HTTP 422 with `approved=false` and publish an event. Infrastructure failures retry, and terminal failures produce governed dead-letter metadata. | More outcome paths require separate tests and monitoring. |
| **Publish supporting-service events only after state changes** | Publish read events; publish nothing | The user limited supporting services to mutation events. Account updates and cycle close publish `AccountStateChanged`; customer changes publish `CustomerContextChanged`; card updates publish `CardUpdated`. | Authorization and notification depend on their local projections staying within the configured freshness bounds. |
| **Decide each account-update event on its own record, not on the pair** | One event per applied update; both events on every applied update | The two rewrites at `app/cbl/COACTUPC.cbl:L4066` and `:L4086` run unconditionally, each writing back the values the caller submitted, so a record whose submitted values equal its fetched values is rewritten with what it already held and has no state change to announce. Publishing regardless makes a reader of the topic read a change that never happened, and it contradicts the AAP's limit of supporting services to mutation events. The comparison is the one `app/cbl/COACTUPC.cbl:L1684-L1768` already draws, applied per record. | A consumer cannot treat either topic as a heartbeat for every update. Reaching the rewrites requires the submitted pair to differ from the fetched pair, so at least one event is always published and no committed write is silent. |
| **Govern eight business event types and one dead-letter envelope** | Limit schemas to the five initial core events | The delivered platform also publishes account, customer-context, and card state changes, as required for supporting-service mutations and notification projection freshness. All runtime wire forms use the same validation gate. | The contract library governs service-owned records that it does not bind to Java classes itself. |

## Runtime, configuration and infrastructure decisions

### Platform and runtime wiring

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| Publish the event through a transactional outbox rather than from the request handler | Publish directly after the write; publish inside a distributed transaction across the database and the broker | The decision row and the event row commit in one local transaction, so a decision can never exist without its event or an event without its decision. The source has an ancestor for the shape: `app/cbl/CORPT00C.cbl:L517-L518` writes to a queue and lets a separate reader pick the work up. ### Terminal delivery and offsets

| Decision | Alternatives considered | Why this choice | Risks accepted |

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| The archive stage copies `target/*.jar` into a directory and then refuses to continue unless exactly one archive arrived | Keep `COPY target/*.jar app.jar`; name the archive with a build argument; copy the whole `target/` directory and select inside the image; check the archive is a boot archive rather than counting | Copying a pattern onto a name is ambiguity-tolerant: measured, with two matches BuildKit keeps whichever sorts last and reports nothing, so a decoy archive named after the real one shipped in place of it and the build still exited 0. Counting is one shell test and it turns that silence into a build failure naming what it found. A build argument would move the version into a second place that has to be raised with `pom.xml`. Copying all of `target/` would send the class files and the reports to the daemon for no gain | The stage now runs one command, so the image build depends on a shell in the runtime image, which the pinned image carries. A single archive with the wrong contents still ships: the guard counts archives and does not read them |
| Each module carries its own `.dockerignore` | Rely on the root ignore file; exclude nothing and accept the transfer; add a `.dockerignore` naming only `src/` | A context has no ignore file unless it carries one, and each image builds from its module directory, so the root file never applied to any of the six builds. Measured before: 85.9 megabytes transferred for an 82-megabyte archive, the difference being `src/`, the class files, the pre-repackage archive and the test reports — none of which any stage reads | A new build-time input has to be added to six files rather than one. Each file lists paths rather than excluding everything and re-including the archive, because an inverted pattern that goes wrong fails by shipping nothing rather than by shipping too much |
| The health probe keeps a curl form and a bash form, and the `wget` form between them is removed | Keep all three; keep `wget` and drop `bash`; install `wget` into the image | `bellsoft/liberica-openjre-debian:25.0.4-9`, the image every `Dockerfile` pins by digest, carries curl and bash and no wget, so that branch could never run: it read as a fallback and was dead text. The bash form stays because it needs no package at all, and it is what would answer if a future base image dropped curl. Installing wget would add a package to an image that installs none | A base image carrying neither curl nor bash would report every container unhealthy. The digest pin is what makes that a deliberate change rather than a surprise |
| The unhealthy tolerance is twelve retries at a ten-second interval, inside a sixty-second start period | Keep twenty-four retries; drop to six; add `restart: on-failure`; leave the start period to absorb it | Twenty-four retries meant a service that stopped answering kept reporting healthy for 240 seconds, which is longer than the whole demonstration it serves. Halving the retry count keeps a wide tolerance for a transient pause while making an outage visible in a time a person watching will notice: measured, a service reported unhealthy 176 seconds after its database was stopped, and recovered 15 seconds after the database returned with no restart | A service unreachable for about three minutes is reported unhealthy, and `restart: unless-stopped` does not restart on health, so an operator still acts. ## Continuous integration decisions

`.github/workflows/ci.yml` is the repository's only workflow, and the repository had no pipeline before it. Rule 1 keeps rationale out of the workflow file, so the choices behind its six stages are recorded here. [Onboarding](onboarding.md) carries the local form of every command the workflow runs.

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| The equivalence suite is its own stage, so six named stages replace one `mvn verify` | Fold every check into a single `verify` stage; run the parity checks only on the default branch; run them on a schedule | The user asked that equivalence testing never be deferred, so the suite needs a stage whose name appears in the run summary and whose failure cannot be read as a compilation error. Two further stages exist for the same reason: 13 `*IT.java` classes in the six service modules run only under Failsafe, and the event schema gate is what keeps a new consumer from breaking an existing one. A single stage would report all of that as one reactor log | Six stages each check out the repository and install the toolchain again, which costs runner minutes that one stage would not |
| Apache Maven 3.9.16 is downloaded and checked against its published SHA-512 sum in every stage | Accept the Maven the runner image ships; add a Maven wrapper to the repository; relax the enforcer range | The build requires `[3.9.16,4.0.0)`, and a hosted runner ships whatever patch its image carries. A runner below the floor would fail the enforcer for an environment reason that reads like a project defect. No wrapper exists in this repository, so the archive is fetched and verified instead | Each stage depends on the Apache archive host being reachable, and the pinned version has to be raised here as well as in `card-platform/pom.xml` |
| Each stage assembles the checksum line before verifying it, rather than handing the published file to `sha512sum --check` | Compare the two digests with a shell string equality test; skip verification; keep a checksum file in this repository | `apache-maven-3.9.16-bin.tar.gz.sha512` holds 128 hexadecimal characters, no file name and no closing newline, and GNU coreutils reads a checksum line as digest, two spaces, file name. Assembling the line keeps the verification inside the tool that owns it, and `--strict` then refuses any other shape. | Every Maven stage builds the modules it needs with `-am` rather than installing the reactor first | Run `install` in the first stage and resolve from the local repository in later stages; publish the archives between stages | `card-platform/equivalence-tests` declares test-scope dependencies on all six services at `${project.version}`, and the aggregator does not manage those coordinates. | The container stage builds all six images, starts them, and publishes none | Push to a registry; sign the images; keep the images only as a build cache; build without starting | The user framed the deliverable as a demonstration rather than a deployment, so the check that matters is that each `Dockerfile` builds **and** that what it builds runs. Publishing would need a registry credential and a write permission the workflow deliberately does not hold, since it grants `contents: read` alone. Building without starting proved compilability only: measured, a stage that ends at `docker build` stays green while every image fails to boot, migrate or serve health. The stage now raises the whole stack from `docker-compose.yml`, reads `/actuator/health` on all six management ports, and removes the stack whether the check passed or not | The stage costs the time a cold stack takes to converge, roughly two minutes, and it needs the fourteen credentials and three encoded identity secrets generated on the runner. Nothing downstream can consume the images, so a deployment target still builds them again |
| One image tag serves the workflow, Compose and Kubernetes: `carddemo/<service>:1.0.0-SNAPSHOT`, the Maven project version | Keep the workflow's own `:ci` tag; use `latest`; let Compose keep its default `<project>-<service>` name; derive the tag from the commit | Three names for one artifact meant the stage's output was consumed by nothing: the workflow built `:ci`, `deploy/k8s` named the project version, and the six Compose services declared no `image:` key at all, so Compose built a seventh name. One tag makes the images the workflow builds the images Compose starts in the same job and the images a cluster expects, and `KubernetesDeploymentContractTest` and `ContinuousIntegrationWorkflowContractTest` both derive it from `card-platform/pom.xml` so the three places cannot drift | A snapshot tag is mutable, which is acceptable for a demonstration and not for a release. The version has to be raised in `pom.xml`, in the six Compose entries and in the six manifests together, and the two contract tests are what report a mismatch |
| Every stage that writes a test report keeps it as a named artifact, with `if: always()` and `if-no-files-found: error` | Retain nothing and read the log; publish a test-report annotation with a third-party action; upload the archives and the images too | A run produces 267 Surefire and Failsafe documents and previously discarded all of them, so a red run left nothing to download and a failure had to be reproduced locally before it could be read. `if: always()` is what makes a failing stage upload rather than skip, and `if-no-files-found: error` turns an empty upload into a failure, because a stage that wrote no report did not run its tests. A third-party annotation action would add a supply-chain dependency to a workflow that currently uses first-party actions alone | Four artifacts per run at a fourteen-day retention consume storage. The six 82-megabyte archives and the six images are deliberately not uploaded: they are rebuilt by one documented command, and uploading them would cost roughly half a gigabyte a run to save a two-minute build |
| `-DskipTests` appears on the compile and packaging stages, and the tests belong to the three stages between them | Run the tests in the compile stage; skip integration tests with `-DskipITs` and rely on one later stage; package with the tests enabled | Those two stages exist to produce class files and archives. Packaging with tests enabled would run the whole suite a second time for no new information | A reader who greps the file for `skipTests` sees two hits and has to read three more stages to confirm nothing is skipped overall |
| The two stages that raise the database and the broker generate the fourteen credentials with the command `.env.example` documents, immediately after copying it | Commit a set of credentials for the pipeline; relax the provisioning refusal when a continuous-integration variable is set; add a second Compose file for the pipeline; drop the two stages and rely on Testcontainers alone | Copying the example file is not enough on its own. Measured: `cp .env.example .env` followed by `docker compose up --detach --wait postgres kafka` leaves the database unhealthy and the stage fails, because the provisioning script refuses a credential the example file publishes. Generating them in the stage keeps the refusal intact and puts no credential in the repository, and reusing the documented command means one place defines it. Measured after: both containers report healthy and the service suites and the parity suite pass against them | Each run holds credentials that exist only for that runner, so a failed run cannot be reproduced by connecting to its database afterwards. The variable list is repeated in the workflow and in `.env.example`, and a new credential has to be added in both |
| The class-file check reads every class file the reactor wrote, collected with `mapfile` and read by one `javap` invocation | Sample one class file with `find -print -quit`; pipe `find` into `head`; run `javap` once per file; read the release from the compiler settings instead | A step declared as `shell: bash` runs under `bash -eo pipefail`, so no form of this check may contain a pipeline whose reader closes early: measured, `find` piped into `head -n 1` exits 141 on 10 of 10 runs because `find` takes SIGPIPE, and the step fails on the shell's status rather than on a class file. Sampling one file avoided that and checked 1 of 413 files, always inside the first module, so a service compiled at another release passed the stage four other stages depend on. `mapfile` with process substitution has no pipeline, and `javap` accepts every path in one invocation: measured 413 files in 1.8 seconds, against roughly two minutes for one invocation per file | The step holds the whole collection in a shell array and one temporary file, which is bounded by the reactor's own output. It reads main class files only; test classes compile under the same property and the enforcer rule covers them |
| The compile release is verified by an enforcer `requireProperty` rule in every module | Add `extra-enforcer-rules` and its `enforceBytecodeVersion`; trust the aggregator property alone; check the release in the workflow only | The plan requires the language level to be verified by the enforcer, and `requireJavaVersion` verifies the running JDK, which says nothing about the release a module compiles at. Measured before the rule: setting `maven.compiler.release` to 21 in one service compiled silently at exit 0 and wrote class files at major version 65. `requireProperty` reads the effective property in every module, ships inside `enforcer-rules` already on the classpath, and therefore keeps `mvn -o` working. `enforceBytecodeVersion` would read the class files themselves, and adding it means a new artifact to resolve and pin | The rule reads a property rather than the bytes, so a compiler argument passed on the command line could still override the release. The workflow's class-file sweep is what reads the bytes |

## Web-surface QA-remediation decisions

A runtime test pass over the six web surfaces raised eighteen findings, six major and twelve minor,
plus one informational item against the ledger balance route. The finding is what a caller saw; the
row below is the choice made in answer to it, and every one of these could reasonably have been made
another way. Where a finding's suggested fix was not taken, the row says so and says why.

### Request strictness on the authorization route

| Decision | Alternatives considered | Why this choice | Risks accepted |

## Cycle-accumulator chain QA-remediation decisions

A runtime test pass measured six consecutive authorizations of 100.00 against an account whose credit
limit is 120.00. All six were approved, taking the account five times past its limit, and the two
billing-cycle accumulators read zero afterwards. The same pass found `GET /accounts/{id}` and
`GET /balances/{id}` reporting balances that differed by every amount ever posted. Both findings had
one cause: no service consumed `transaction.posted` into the account record, so the only copy of
`ACCTDAT` that the credit-limit rule can reach was never moved by a posting.

### Where the posted amount is applied

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| The account service consumes `transaction.posted` and applies the amount to its own `account` row, reproducing `app/cbl/CBTRN02C.cbl:L545-L560` | Have the authorization service consume `transaction.posted` and write its own snapshot; have the ledger publish the accumulators it already holds; have the ledger accept the value columns of the account service's `AccountStateChanged` | The account service owns the record, and the amount belongs in it whether or not any rule reads it. Applying it here fixes the balance `GET /accounts/{id}` reports and the accumulators reason code 102 reads with one change, through the `AccountStateChanged` path authorization already consumes. Authorization consuming the posted event would fix the rule and leave the account read wrong, and would make authorization derive state it does not own. The ledger publishing accumulators would put two producers on one contract and still leave the account read wrong | One more consumer group to operate, and a chain of three asynchronous hops between a posting and the snapshot the next authorization reads. Onboarding pitfall 5 documents the spacing that implies for a live demonstration |
| The listener applies the event's `amount` and never its `newBalance` | Copy `newBalance` into the account row; copy it and reconcile on divergence | A balance copied across a service boundary has two owners and no way to settle a disagreement. An amount applied to a locally held balance keeps one owner, and the processed-event marker makes the repeat harmless rather than the arithmetic having to be idempotent | The two balances can diverge if a posted event is ever lost outright rather than redelivered. The marker plus the dead-letter route make that visible instead of silent |
| The ledger continues to ignore the value columns of an `ACCOUNT_UPDATED` event on a projection row it already holds | Apply them like any other state change; apply them only when they are newer | The ledger applied the same amount itself a moment earlier. Taking the account service's copy would overwrite a correct value with one that is behind by every posting the account service has not yet heard about, and the two services would chase each other. `messaging/AccountStateChangedConsumer` in that module documents the reasoning at length | The two copies of the accumulators can differ transiently. Neither is read by a decision the other makes, so the difference has no consumer |
