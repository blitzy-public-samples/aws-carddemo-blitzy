# Decision Log

Rule 1 requires one place for every non-trivial design choice. A choice belongs here when a competent engineer could reasonably choose another approach. Source-to-target mapping lives in the [traceability matrix](traceability-matrix.md), while open source ambiguities live in [business-rule flags](business-rule-flags.md). Code comments describe behavior and point here for rationale.

**How to read a superseded row.** This log grew as the platform did, and a later decision sometimes replaced an earlier one. A replaced row keeps its evidence and opens with **SUPERSEDED**, which names the row now in force. Only that named row describes the delivered behaviour. Nothing else in this log is superseded: every other row states what the code does today.

| **C3 — Maven mono-repo under `card-platform/`** | One repository per service | One repository makes the untouched legacy boundary auditable and keeps contracts, fixtures, services, and parity tests versioned together. | Services share a repository release cadence even though their Maven dependencies remain separate. |
| **C4 — JSON Schema Draft 2020-12 with build-enforced compatibility** | Avro with a schema registry; unchecked JSON | JSON remains readable in a console demonstration. Publish and consume validation plus compatibility tests enforce the contract without another runtime container. | A producer outside this build could ignore the compatibility gate. |
| **C5 — Representational State Transfer with JSON** | gRPC | A caller can demonstrate each synchronous route with `curl` and no generated client. | Client types are not compiled from a remote procedure contract. |
| **C6 — Exhaustive tables with short prose** | Exhaustive narrative prose | Rule 1 requires complete coverage, while Rule 5 rejects repetition. Tables carry enumeration without hiding gaps in paragraphs. | Readers who skim tables can miss a narrow exception. |

## Migration strategy

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Parallel reimplementation with equivalence verification** | A strangler-fig facade routing traffic to the mainframe | The user required the services to “not call into the mainframe at runtime.” Fixtures and documented rules therefore form the executable comparison baseline. | Behavior absent from both fixtures and documented rules needs a synthetic test or remains unverified. The precision boundary is the concrete instance: no cycle balance in the 300-record daily fixture reaches one billion, so a constructed case carries that proof. |
| **Authorization logic is a declared synthesis** | Invent behavior for `COPAUA0C`; treat the brief’s name as an existing program | `COPAUA0C` and transaction `CP00` are absent. Rules come from `CBTRN02C`, request fields from `COTRN02C`, and the signon fork from `COSGN00C`. | There is no synchronous source program against which to compare the whole request path. |
| **Authorization reads local projections and calls no supporting service** | Synchronous account-service and card-service clients | Existing repositories, freshness fields, and tests already defined event-maintained copies. Outbound clients would add credentials and runtime coupling. | Authorization decisions can reflect projection lag. The account projection records event provenance and observation time. |
| **Two events refresh authorization state, and `CardUpdated` refreshes an observation rather than a mapping** | Consume only `AccountStateChanged`; upsert `card_xref` from `CardUpdated`; call the card service synchronously | Authorization consumes both streams. `AccountStateChanged` replaces every value column of `account_credit_snapshot`, because a decision reads all of them. `CardUpdated` cannot do the same for `card_xref`: it carries a masked card number, while that table is keyed by the full sixteen characters. | **Fraud detection is marked net new** | Manufacture lineage from a nearby transaction program | No source program scores risk, checks velocity, or evaluates fraud rules. Honest traceability distinguishes design intent from migrated behavior. | Fraud tests verify the new contract, not COBOL parity. |

## Arithmetic and numeric fidelity

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| **Reproduce the tolerant date policy, including its undocumented `2513` acceptance** | Accept a date on severity `'0000'` alone and treat the second branch as a defect; reject the branch and flag it | Four call sites read the tolerant policy — `app/cbl/COTRN02C.cbl:L397-L400` and `:L417-L420`, and `app/cbl/CORPT00C.cbl:L396-L399` and `:L416-L419` — and each accepts a date when the severity text is `'0000'` **or** when the message-number text is `'2513'`. No comment in the source explains the second condition. Dropping it would refuse dates the source accepts, which is an equivalence break, and transformation rule T7 requires reproducing a defect and flagging it rather than correcting it quietly. The mask the tolerant policy passes is `WS-DATE-FORMAT PIC X(10) VALUE 'YYYY-MM-DD'` | The platform accepts a date on a condition nobody can explain. `CobolDateValidatorTest` includes a case that passes only because of the `2513` branch, so the tolerance cannot be removed unnoticed, and the register carries it as an item a human owner must decide |
| **Carry the strict date policy separately, on its own mask** | Collapse both policies into one method with a flag; apply the tolerant policy everywhere | The source holds two acceptance policies over the same called program and they disagree. The strict one accepts a date only on a numeric severity of zero, reads its mask as `WS-DATE-FORMAT PIC X(08) VALUE 'YYYYMMDD'` from `app/cpy/CSUTLDWY.cpy:L58-L59`, and has exactly one call site, `app/cpy/CSUTLDPY.cpy:L298`, which holds no `'2513'` branch. Two different masks and two different acceptance conditions are two contracts, so `CobolDateValidator` exposes `isAcceptedByTolerantPolicy` and `isAcceptedByStrictPolicy` and no method takes a policy argument | A caller has to choose a policy, and choosing the wrong one changes which dates are accepted. The two mask constants are public, so a call site names the mask it reproduces |
| **Timestamp shapes come from `CSDAT01Y`, which is a live authority rather than a presentation helper** | Derive the shapes from `CBTRN02C` alone; treat the copybook as presentation-only and excluded | Two 26-character timestamp shapes coexist and they are not interchangeable. `WS-TIMESTAMP` at `app/cpy/CSDAT01Y.cpy:L42-L55` fixes the inbound origin shape, separator by separator, including the space its `FILLER` at `:L48` puts between the date and the time. `DB2-FORMAT-TS` at `app/cbl/CBTRN02C.cbl:L159-L174` fixes the processing shape, with hyphens and dots and two significant fractional digits. `BillPaymentEquivalenceTest` reads the copybook as the oracle for the first shape, so classifying it as presentation-only was wrong about a document the suite depends on | A copybook the presentation layer also uses is in scope for one section of its content. The traceability matrix lists its live consumers so the reason is discoverable |
| **Truncate every monetary result toward zero** | `RoundingMode.HALF_UP`; `RoundingMode.HALF_EVEN`; floor | `ROUNDED` appears zero times across all 28 programs in `app/cbl/`. COBOL therefore truncates stored arithmetic results. | A future “cleanup” of the rounding mode can change cents without a type error. Equivalence tests detect that change. |
| **Serialize money as a two-place decimal string** | JSON number | Common JSON clients decode numbers through binary floating point. Decimal strings preserve the fixed-point contract across languages. | Consumers must parse the value as a decimal rather than as a native floating-point number. |
| **Derive precision and scale from each Picture clause** | Store cents in integers; use one wide decimal type everywhere | `PIC S9(10)V99`, `PIC S9(09)V99`, and `PIC S9(04)V99` map to `NUMERIC(12,2)`, `NUMERIC(11,2)`, and `NUMERIC(6,2)`. | A source clause read incorrectly can propagate into entities, schemas, migrations, and tests. |
| **Keep display identifiers as fixed-width text** | Numeric identifier columns | Account, customer, merchant, and category identifiers retain leading zeros and are compared as display fields. | Text storage does not provide numeric ordering, which these identifiers do not need. |
| **Reproduce tolerant numeric input parsing** | `new BigDecimal(String)` | `FUNCTION NUMVAL-C` accepts separators and currency notation at `app/cbl/COTRN02C.cbl:L383`; `app/cbl/COACTUPC.cbl:L2201` gates the same conversion. | Inputs rejected by stricter systems remain acceptable for parity. |

## Runtime, configuration and infrastructure decisions

### Platform and runtime wiring

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| Publish the event through a transactional outbox rather than from the request handler | Publish directly after the write; publish inside a distributed transaction across the database and the broker | The decision row and the event row commit in one local transaction, so a decision can never exist without its event or an event without its decision. The source has an ancestor for the shape: `app/cbl/CORPT00C.cbl:L517-L518` writes to a queue and lets a separate reader pick the work up. It also has the gap: `app/cbl/CBTRN02C.cbl:L440-L442` performs three writes with no rollback, and every file in `app/csd/CARDDEMO.CSD:L3-L9` declares `RECOVERY(NONE) JOURNAL(NO)` | An event is published after the commit rather than with it, so a consumer sees it late rather than never. Two writes per call instead of one |
| All five producer services use one claimed-row relay state machine | Let each relay poll unlocked rows; rely on one replica; keep the older pessimistic-lock query without durable claim state | A rolling deployment or manual scale-out can run two relay instances over one table. `FOR UPDATE SKIP LOCKED` gives each transaction a disjoint due batch, `claimed_by` and `claimed_at` make the winner durable, and the claim timeout recovers work from an instance that stopped. The attempt count, due time and bounded backoff prevent one refused row from being retried on every sweep. One explicit `TransactionTemplate` boundary also keeps counters and timers outside the database transaction, so a rollback cannot report success | A broker round trip holds a database transaction and row locks. A send that succeeds before the database commit fails can be repeated, so consumers still need processed-event idempotency |
| Every service applies one bounded `service` common tag to application and framework meters | Tag only hand-written meters; rely on scrape-target labels; leave services inconsistent | One collector receives application, Java Virtual Machine, HTTP, and database meters from all six services. A registry customizer applies the same dimension before any meter is registered, so every series can be grouped with one query and no service-specific exception | The service name is present both in the metric prefix and as a tag on hand-written series. The duplication is bounded to six values |
| Readiness checks the database, Kafka, expected listener containers and terminal outbox state, while liveness checks process state alone | Keep Boot's generated `readinessState` group; put external dependencies in liveness; probe the aggregate health endpoint | A process can stay alive after its database or broker is lost, a listener is stopped, or a relay abandons an event. Those states cannot serve the platform contract and must withdraw the instance without restarting a healthy Java virtual machine. Database acquisition and Kafka discovery have explicit short deadlines, and Compose and Kubernetes probe the same readiness group | A transient shared dependency outage can withdraw every replica at once. An abandoned outbox row keeps a producer unready until an operator resolves it; that is deliberate because later events must not overtake the failed row |
| Compose reads `.env` for interpolation but every application container receives an explicit environment map | Attach `.env` to every service with `env_file`; split one dotenv file per service; put all credentials in the shared environment anchor | Compose interpolation can select one service's database and broker credentials without injecting the source variables themselves. Removing `env_file` prevents the PostgreSQL superuser, Kafka administrator and five sibling service credentials from entering each application container, while one checked-in map keeps the demo runnable from a single operator file | The six service blocks repeat their own settings, and adding a new application property requires adding it to the owning block. A build contract checks the active relay, consumer and retention keys so an omission fails before deployment |
| Dotenv bcrypt values are single quoted | Leave generated hashes unquoted; escape every dollar sign as `$$` | A generated bcrypt value contains several dollar signs. Compose expands dollar-prefixed text in unquoted and double-quoted dotenv values, corrupting a valid hash before Spring Security reads it. Single quotes preserve the generated value character for character and are easier to paste correctly than escaping each dollar sign | The quotes must remain around the replacement value. The example and a Compose runtime check demonstrate that requirement |
| Kubernetes stores the single demo broker's KRaft log, topic records and committed offsets on a `ReadWriteOnce` persistent claim | Keep `emptyDir`; rebuild broker state on every Pod replacement; require an external managed broker | A Deployment replacement is routine maintenance, not an instruction to erase every topic and every consumer position. A claim also keeps the configured KRaft cluster identifier paired with the metadata it names. The standard-cluster manifest remains self-contained and uses the cluster's default storage class | The 2 GiB claim is single-node demo storage, not a highly available broker design. A cluster without a default storage class leaves the claim pending, and deleting the claim remains the explicit destructive reset |
| Each service mounts its own server keystore while all services share one trust-only Secret | Mount one shared keystore in all six Pods; duplicate the same truststore into six Secrets; terminate Transport Layer Security outside the services | The six Services have different Domain Name System names, so each certificate must identify its own endpoint and each private key must stay within that workload's boundary. The certificate authority and truststore are public trust material rather than service identity, so one trust-only Secret avoids six copies without sharing a private key | Operators must issue and rotate six certificates and six keystore passwords. The checked-in Secret file contains placeholders only and must be replaced before deployment |
| Kubernetes uses `imagePullPolicy: Never` for the six locally built demo images | `IfNotPresent`; `Always`; require a registry before the demo can run | The repository defines local Docker builds and no image registry. `Never` makes that contract explicit. A node either has the exact image the operator built, or the Pod fails. The alternative is silently pulling a same-named image from a default registry, or running a stale cached tag | Every node that can schedule a service must have the image preloaded. A multi-node or remote cluster needs a registry and a deliberate pull-policy change |
| Every service image tag in Kubernetes is the Maven project version | Keep the stale `1.0.0` literal; use `latest`; version the deployment independently | The build produces `1.0.0-SNAPSHOT`, so a manifest naming `1.0.0` asks Kubernetes for an artifact this reactor did not build. Deriving the tag from `project.version` keeps the build command, the six manifests and the deployment contract on one version | A snapshot tag is mutable and is suitable only for this demo. A production release should publish immutable versioned images, preferably with a digest |
| Producer services enforce outbox and processed-marker retention with scheduled, explicit transactions | Keep the settings as documentation only; remove the settings; run one platform-wide database job | A configured horizon with no caller is false configuration. Each service owns its schema, so each service deletes only its own published rows and markers. Two explicit `TransactionTemplate` calls avoid the self-invocation trap that would leave modifying queries outside a transaction | Five small scheduled components repeat the same shape. A failed sweep delays deletion until the next interval but never blocks business traffic |
| Every consumer records processed event identifiers | Rely on broker exactly-once semantics; deduplicate in memory | Kafka delivers at least once, and a rebalance or a restart mid-batch redelivers. The source has no duplicate detection at all: a replayed feed drives the transaction write at `app/cbl/CBTRN02C.cbl:L562-L579` into a duplicate key and straight to the abend routine. An in-memory guard loses its contents on the restart that causes the redelivery | One extra table and one extra read per delivery. The marker table grows and needs a retention horizon |
| Money is a decimal string on the wire, never a JSON number | JSON number; integer minor units | Most readers deserialize a JSON number into a binary floating-point double, which reintroduces the representation this platform exists to avoid. A string with a two-decimal pattern in the schema cannot be widened into a double by accident | Consumers must parse rather than read a number directly |
| All monetary arithmetic truncates toward zero | `HALF_UP`; `HALF_EVEN` | The `ROUNDED` phrase appears zero times across all twenty-eight programs in `app/cbl/`, so every arithmetic store in the source truncates. `HALF_UP` is the reflexive choice in Java and it breaks equivalence by one cent, silently | A reader unfamiliar with the source will find `RoundingMode.DOWN` surprising, which is why one test asserts that half-up rounding produces a different answer |
| The account identifier is the Kafka message key on every event that resolves an account, and the transaction identifier keys the one form that does not | A single key form for every event; no key | Kafka guarantees order within a partition only, and the ledger's balance updates for one account must not be reordered, so an account key is what keeps them on one partition. A reason-0100 decline resolves no account, and `transaction-declined-v2.json` fixes both its code and its text to `0100` for exactly that case. Inventing an account identifier to fill the key would put a false value on the wire, and omitting the key would spread one account's events across partitions | Two sanctioned key forms exist, so a consumer reading the key must distinguish them by width: eleven digits for an account, sixteen for a transaction |

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |

## Continuous integration decisions

`.github/workflows/ci.yml` is the repository's only workflow, and the repository had no pipeline before it. Rule 1 keeps rationale out of the workflow file, so the choices behind its nine stages are recorded here. Six of the nine predate the security review; the three it added, and the two controls it added to the container stage, are recorded under Supply chain and delivery decisions below. [Onboarding](onboarding.md) carries the local form of every command the workflow runs.

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| The equivalence suite is its own stage, so nine named stages replace one `mvn verify` | Fold every check into a single `verify` stage; run the parity checks only on the default branch; run them on a schedule | The user asked that equivalence testing never be deferred, so the suite needs a stage whose name appears in the run summary and whose failure cannot be read as a compilation error. Two further stages exist for the same reason: the `*IT.java` classes in the six service modules run only under Failsafe — there are 15 of them today, and the stage is defined by the naming pattern rather than by a count, so adding one needs no edit here — and the event schema gate is what keeps a new consumer from breaking an existing one. A single stage would report all of that as one reactor log | Nine stages each check out the repository, and the eight that run Maven install the toolchain again, which costs runner minutes that one stage would not |
| Apache Maven 3.9.16 is downloaded and checked against its published SHA-512 sum in every stage | Accept the Maven the runner image ships; add a Maven wrapper to the repository; relax the enforcer range | The build requires `[3.9.16,4.0.0)`, and a hosted runner ships whatever patch its image carries. A runner below the floor would fail the enforcer for an environment reason that reads like a project defect. No wrapper exists in this repository, so the archive is fetched and verified instead | Each stage depends on the Apache archive host being reachable, and the pinned version has to be raised here as well as in `card-platform/pom.xml` |
| Each stage assembles the checksum line before verifying it, rather than handing the published file to `sha512sum --check` | Compare the two digests with a shell string equality test; skip verification; keep a checksum file in this repository | `apache-maven-3.9.16-bin.tar.gz.sha512` holds 128 hexadecimal characters, no file name and no closing newline, and GNU coreutils reads a checksum line as digest, two spaces, file name. Measured: handing the published file to `sha512sum --check` exits 1 with "no properly formatted checksum lines found", which failed every job at its second step, so nothing after it ever ran. Assembling the line keeps the verification inside the tool that owns it, and `--strict` then refuses any other shape. Taking the first field with `awk` also accepts the two-field form other projects publish. A shell equality test would work and would move the comparison out of that tool, where a typo reads as a passing string comparison rather than as a failed checksum | The step now depends on the published file's first field being the digest. `ContinuousIntegrationWorkflowContractTest` pins the assembled form and asserts the bare-digest form is absent, so the defect cannot return unnoticed |
| Every Maven stage builds the modules it needs with `-am` rather than installing the reactor first | Run `install` in the first stage and resolve from the local repository in later stages; publish the archives between stages | `card-platform/equivalence-tests` declares test-scope dependencies on all six services at `${project.version}`, and the aggregator does not manage those coordinates. | The container stage builds all six images, starts them, and publishes none | Push to a registry; sign the images; keep the images only as a build cache; build without starting | The user framed the deliverable as a demonstration rather than a deployment, so the check that matters is that each `Dockerfile` builds **and** that what it builds runs. Publishing would need a registry credential and a write permission the workflow deliberately does not hold, since it grants `contents: read` alone. Building without starting proved compilability only: measured, a stage that ends at `docker build` stays green while every image fails to boot, migrate or serve health. The stage now raises the whole stack from `docker-compose.yml`, reads `/actuator/health` on all six management ports, and removes the stack whether the check passed or not | The stage costs the time a cold stack takes to converge, roughly two minutes, and it needs the fourteen credentials and three encoded identity secrets generated on the runner. | One image tag serves the workflow, Compose and Kubernetes: `carddemo/<service>:1.0.0-SNAPSHOT`, the Maven project version | Keep the workflow's own `:ci` tag; use `latest`; let Compose keep its default `<project>-<service>` name; derive the tag from the commit | Three names for one artifact meant the stage's output was consumed by nothing: the workflow built `:ci`, `deploy/k8s` named the project version, and the six Compose services declared no `image:` key at all, so Compose built a seventh name. One tag makes the images the workflow builds the images Compose starts in the same job and the images a cluster expects, and `KubernetesDeploymentContractTest` and `ContinuousIntegrationWorkflowContractTest` both derive it from `card-platform/pom.xml` so the three places cannot drift | A snapshot tag is mutable, which is acceptable for a demonstration and not for a release. ### Request strictness on the authorization route

| Decision | Alternatives considered | Why this choice | Risks accepted |

### Readiness under a dependency outage

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |

## Cycle-accumulator chain QA-remediation decisions

A runtime test pass measured six consecutive authorizations of 100.00 against an account whose credit
limit is 120.00. All six were approved, taking the account five times past its limit, and the two
billing-cycle accumulators read zero afterwards. The same pass found `GET /accounts/{id}` and
`GET /balances/{id}` reporting balances that differed by every amount ever posted. Both findings had
one cause: no service consumed `transaction.posted` into the account record, so the only copy of
`ACCTDAT` that the credit-limit rule can reach was never moved by a posting.

### Where the posted amount is applied

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| The account service consumes `transaction.posted` and applies the amount to its own `account` row, reproducing `app/cbl/CBTRN02C.cbl:L545-L560` | Have the authorization service consume `transaction.posted` and write its own snapshot; have the ledger publish the accumulators it already holds; have the ledger accept the value columns of the account service's `AccountStateChanged` | The account service owns the record, and the amount belongs in it whether or not any rule reads it. Applying it here fixes the balance `GET /accounts/{id}` reports and the accumulators reason code 102 reads with one change, through the `AccountStateChanged` path authorization already consumes. Authorization consuming the posted event would fix the rule and leave the account read wrong, and would make authorization derive state it does not own. The ledger publishing accumulators would put two producers on one contract and still leave the account read wrong | One more consumer group to operate, and a chain of three asynchronous hops between a posting and the snapshot the next authorization reads. Onboarding pitfall 5 documents the spacing that implies for a live demonstration |
| The listener applies the event's `amount` and never its `newBalance` | Copy `newBalance` into the account row; copy it and reconcile on divergence | A balance copied across a service boundary has two owners and no way to settle a disagreement. An amount applied to a locally held balance keeps one owner, and the processed-event marker makes the repeat harmless rather than the arithmetic having to be idempotent | The two balances can diverge if a posted event is ever lost outright rather than redelivered. The marker plus the dead-letter route make that visible instead of silent |
| The ledger continues to ignore the value columns of an `ACCOUNT_UPDATED` event on a projection row it already holds | Apply them like any other state change; apply them only when they are newer | The ledger applied the same amount itself a moment earlier. Taking the account service's copy would overwrite a correct value with one that is behind by every posting the account service has not yet heard about, and the two services would chase each other. `messaging/AccountStateChangedConsumer` in that module documents the reasoning at length | The two copies of the accumulators can differ transiently. Neither is read by a decision the other makes, so the difference has no consumer |

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| One pass of the authorization relay is several transactions: one committed claim, no transaction at all around the sends, and one short transaction per result | Keep the whole pass in one transaction; move the sends onto separate threads | The single transaction held a connection and every row lock of the batch for the sum of its broker waits, which with a hundred rows and a ten-second wait each is roughly a thousand seconds. ## Interface-review remediation decisions

These cover the notification history route, the account surface and the card surface. The review that
prompted them found the notification route keyed on a value no requirement names, a body wider than the
required shape, a page size that truncated a per-card total, and a caching header the document
described and no response carried. On the account surface it found a read schema narrower than the rows
it returns, required lists shorter than the bodies written against them, request schemas the reader did
not enforce, an identifier promised as nine digits and checked as nine characters, a complete Social
Security Number in two published examples, and prose about the error body that two of its own answers
contradict. On the card surface it found two required routes absent and body-driven substitutes in
their place, a retryable write answered as a defect, a named filter accepted and then dropped, an
expiry range the schema did not hold, a read that refused a card over a relationship the source never
tests, and eight complete seeded card numbers in published examples.

### The notification history route

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| The route carries the card number, and the read model stays keyed on the token derived from it | Key the route on the card token, as before; key the read model on the card number too; publish both and let a caller choose | The required route is `GET /notifications/{cardNumber}`, and the path value is `TRNX-CARD-NUM PIC X(16)` at `app/cpy/COSTM01.CPY:L22`, the first part of the key `KEYS(32 0)` at `app/jcl/CREASTMT.JCL:L30` declares. `PanMasker.cardToken` is a keyed one-way derivation, so the route resolves the stored key on every request and no card number is stored, logged or returned. Storing the card number instead would put a full Primary Account Number in a key column, a primary-key index and every seed file | A card number now reaches a request path, so it reaches an access log, a reverse proxy log, a trace and a browser history of anything in front of this service. The document says so, and `suggested-next-tasks.md` carries the deployment guidance a person has to apply |
| The ownership rule derives the token before it looks for an authority | Grant on a `SCOPE_CARD_` authority naming a card number; add a second authority kind for a card number; move the check into the handler | A configured authority names a card token, which `.env.example` already ships and which no card number can be recovered from. Deriving inside the rule keeps the authority list free of card numbers and keeps the check in the filter chain, ahead of every handler, where no handler can forget it | A path value that cannot be tokenized denies rather than answering 400, so a caller holding no authority learns nothing about which values exist. A missing deployment key raises rather than denying, because that is a fault of the deployment and not a decision about the caller |
| The response covers the whole history of one card and declares no paging parameter | Keep `pageSize` and add a cursor and a next-page flag; keep `pageSize` and refuse a value above its maximum; keep the parameter and total every row anyway | `app/cbl/CBSTM03A.CBL` reads every row of one card between two key breaks and `app/cbl/CBSTM03A.CBL:L429` totals all of them, so a count and a total over part of a history describe a statement the source never produced. The retention sweep bounds the table, `NotificationRenderer.MAXIMUM_STATEMENT_ROWS` still bounds one rendered alert, and a stray `?pageSize=` is neither read nor refused, which is what a route declaring no query parameter means |
| The body names the card once, on the envelope, and carries four members with twelve per entry | Keep the card token on the envelope; keep the masked number on every entry; keep both and mark them optional | The required shape is four envelope members and twelve entry members. Repeating the masked number on every entry restated one value per row of a history that is already keyed by that card | A caller that read `cardToken` from a response has nothing to read it from. No caller in this repository did, and no route consumes it |
| The successful response documents the four caching directives Spring Security writes, rather than `no-store` alone | Set `Cache-Control: no-store` on the response and leave the document; document `no-store` and accept the mismatch | `headers().cacheControl()` installs `CacheControlHeadersWriter`, which writes `no-cache, no-store, max-age=0, must-revalidate` together with `Pragma` and `Expires`. Measured against that writer directly: a response with no header of its own receives all four directives, and one that sets `no-store` first keeps it, which is why the 401 and 403 the chain writes by hand still document `no-store`. The document moved because the code was right | A reader of the document sees a longer value than the intent behind it. The description names the writer, so the four directives read as one policy rather than four decisions |

## Security-review remediation decisions

### Who may authorize a transaction

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| `POST /authorizations` requires `ROLE_ACQUIRER` or `ROLE_ADMIN`, and a new acquirer identity carries that role | Keep `hasAnyRole(USER, ADMIN)`; require the caller to hold `SCOPE_ACCOUNT_<id>` or `SCOPE_CARD_<token>` for the card it presents; resolve the card and then compare it against the caller's scopes inside `AuthorizationService` | The route names its card in the request body, so no path variable carries an identifier an ownership scope can be compared against, and role alone therefore decided the request. An ordinary cardholder identity holding `ROLE_USER` could authorize against any account in the cross-reference and leave a durable decision and a published event behind it. Scoping the route to the presented card would contradict what the route is for: an acquirer legitimately authorizes every card the platform holds, and a point-of-sale network holds no cardholder entitlement. Separating the workload identity from the cardholder identity states that distinction in configuration rather than in a comment | One more identity to configure and one more password hash to generate. A deployment that grants `ROLE_ACQUIRER` to a human identity re-creates the finding, so the role is documented as a machine credential in `.env.example`, `30-configmap.yaml` and the service README |
| The entitlement check inside the decision path passes `ROLE_ACQUIRER` as well as `ROLE_ADMIN` | Grant the acquirer identity `ROLE_ADMIN`, as the entitlement rule originally assumed; grant the acquirer an ownership scope over every seeded card; leave the check admitting the administrator alone | Two additions met here. `domain/CallerEntitlement` was written while an acquirer client was configured as an administrator, so it passed one authority. The security review that followed gave the acquirer a role of its own, so that it reaches this route and no other. Passing only the administrator would have left the route admitting the acquirer at the chain and refusing every call it made, which is a route nobody can use. Granting the acquirer `ROLE_ADMIN` instead would undo the separation the review made, and scoping it to every card would put fifty ownership authorities into configuration and still fail for a card the platform issues next. `RequestCaller.reachesEverySubject` therefore admits both names, and `SecurityConfigTest` holds them in step with the route rule | The acquirer reaches every card the platform holds, which is what the route is for and what `.env.example`, `30-configmap.yaml` and the service README each state. A deployment granting that role to a human identity re-creates the finding the review closed |
| The role check is not replaced by the decline rules that follow it | Rely on reason 0100, which refuses a card the cross-reference does not carry | A refusal is still a durable decision row, a published `TransactionDeclined` event and three downstream consumers doing work. The rules bound which cards resolve, not who may ask | The rules and the role check overlap for a card that does not exist, which costs one comparison |
| The authorization description publishes its security scheme, its requirement and its 401 and 403 answers | Leave the contract undocumented, as before; document the statuses without the scheme | Five of the six services already published a scheme, and this one — the only route a client calls directly — did not. A document that describes a route and omits its authentication tells every reader, and every generated client, that the route is open | The description now restates what `config/SecurityConfig` expresses. `OpenApiContractTest` compares the two, so the duplication is checked rather than merely written |

### What the sensitive-value screen reads

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| The screen removes any run of characters standing between two digits, rather than a named set of separators | Add the decimal point and the solidus to the existing space-and-hyphen set; strip every non-digit; keep the value as written and rely on the schema patterns | A named set can only hold the separators somebody thought of, and free text admits every printable character: `4111.1111.1111.1111` and `020.97.3888` passed both the publish and the consume screen and reached Kafka, an outbox row, a ledger row and the notification renderer. Removing whatever stands between two digits is independent of the spelling. Stripping every non-digit would instead join the digit groups of ordinary sentences, so the two lookarounds requiring a digit on each side are what keep `REF 1234 SEQ 5678 LOT 9012` in three runs | A free-text value that legitimately holds twelve or more digits with nothing but punctuation between them is now refused. A monetary amount reaches twelve digits only at ten dollars of magnitude with cents, which no merchant name, city or description carries, and a refusal is a 400 rather than a silent disclosure |
| The value is also read under Unicode NFKC normalization | Read the value as written alone; reject every non-ASCII character in every screened value | A full-width digit renders as a digit to a reader and a compatibility separator renders as a separator, so a value that looks like a card number was one to everybody except the screen. Normalizing first costs one pass and closes the whole class. Refusing non-ASCII outright is already what a typed free-text field does — its record constrains the value to `^[ -~]*$` — but the `extensions` subtree is open by design and is the path these values arrive on | Normalization is not free on a hot publish path. It runs only after the value as written has already been screened and found clean, so an ordinary event pays one pass over one short string |
| Both screens keep the twelve-digit floor rather than bounding the run at nineteen | Bound the run to the twelve-to-nineteen digits a card number occupies | An upper bound tells a caller how to smuggle a card number: pad it. A floor with no ceiling refuses the padded form too | A digit run longer than nineteen characters is refused as well, and no property this platform screens carries one |

### Which password encodings authenticate

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| Every service builds its own `DelegatingPasswordEncoder` over an allowlist of `bcrypt` and `pbkdf2@SpringSecurity_v5_8`, in place of Spring Security's stock factory | Keep the stock factory and refuse unwanted prefixes at start-up only; keep the factory and set a fallback encoder; encode with one algorithm and map no others | The stock factory maps ten identifiers, and eight of them exist so that a deployment holding legacy hashes can migrate off them: `noop` stores a password in plain text, and `MD4`, `MD5`, `SHA-1`, `SHA-256`, `sha256` and `ldap` are unsalted or single-pass digests. | `argon2` and `scrypt` are not on the allowlist, although both are adaptive | Add both; add both and add Bouncy Castle to every service | Both implementations call Bouncy Castle, which is not a dependency of this platform and is not among the artifacts section 0.5.1 of the plan names. | A `bcrypt` hash must declare a cost of at least ten, checked by parsing the value at start-up | Accept any cost; require twelve; check the cost only in review | Cost is logarithmic, so a hash at cost four is 64 times cheaper to guess than one at ten, and nothing in the encoder refuses it. ### What makes a state-changing request first-party

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |
| Every service requires a non-simple request header, first-party fetch metadata and a matching `Origin` on `POST`, `PUT`, `PATCH` and `DELETE`, with `config/CrossSiteRequestFilter` enforcing all three | Enable Spring Security's synchronizer-token protection; move the business surface onto a bearer token a browser does not attach by itself; grant no cross-origin policy and call the reads safe, as before; require only the header; require only `Origin` | HTTP Basic is the credential this platform authenticates with, and a browser attaches a cached one to a request a page made without being asked. An auto-submitting form on any other site could therefore reach `POST /accounts/{accountId}/cycle-close` and zero both cycle accumulators, and the absent cross-origin policy does not stop it: a form submission is sent regardless of whether the page may read the answer. Token protection needs a prior safe request to hand the token out and a session or a cookie to bind it to, and this surface is stateless by design. Replacing Basic with a bearer token is the better answer and is a larger change than this platform's identity model has: `app/cbl/COSGN00C.cbl:L223` compares a stored password directly, and the migrated signon reproduces that comparison. Of the three conditions the header is the one that always holds — a form cannot set a header at all, and a cross-origin script that set one turns the call into a preflight no chain here grants — while fetch metadata and `Origin` refuse the forged call earlier and cost nothing to test | A non-browser client has to send one header it did not send before. Every `curl` example in this repository carries it, the five state-changing operations declare it in their OpenAPI parameters, and the refusal is documented in each service README and in onboarding pitfall 11. The header's value is never checked, so it is not a secret and does not authenticate anything — it is a capability check on the caller, and it is exactly as strong as the browser rule that a form cannot set a header |
| The filter carries the default component order, so it runs after the security chain | Order it ahead of the chain so a forged call never reaches authentication; order it with `RequestRateCeilingFilter` | A forged cross-site call is by definition authenticated, so the check has to precede the state change and not the credential check. Running after the chain also keeps the answers in the order a caller expects: a request with no credential still receives 401 rather than a cross-site refusal, which is what `config/RequestBodyCeilingFilter` already does | An authenticated forged call pays one bcrypt verification before it is refused. The rate-ceiling filter bounds how many such calls one source may make, which is the control that limits the cost |
| Safe methods pass untouched and no path is exempted | Exempt the actuator base path explicitly; apply the check to every method | `GET`, `HEAD`, `OPTIONS` and `TRACE` change nothing, and no chain on this platform grants a cross-origin policy, so a browser withholds a read's answer from the page that asked for it. Every management endpoint this platform exposes is a read, so exempting a path would add a list to maintain and change no outcome | A state-changing management endpoint added later would need the header like any other write. Only `health`, `metrics` and `prometheus` are exposed, and all three are reads |
| The refusal is 403 carrying the same fixed problem document as every other refusal, naming no route, header or identifier | Name the condition that refused, so a caller can correct it; answer 400 because the request is malformed rather than forbidden | A body that says which of the three conditions refused tells an attacker which one to work on next. One body for all three discloses nothing, and it matches what `config/SecurityConfig` already writes for an unauthorized or forbidden request. 403 is the truthful status: the request was well-formed and this client may not make it | A first-party client that forgot the header reads a refusal that looks like a role refusal. Onboarding pitfall 11 and the six service READMEs name the header as the first thing to check, and every `429` and `403` this control writes is counted separately so the cause is visible in the metrics |

### How much of a service one caller may consume

| Decision | Alternatives considered | Why this choice | Risks accepted |
| --- | --- | --- | --- |

| The filter runs at `SecurityFilterProperties.DEFAULT_FILTER_ORDER` minus one, ahead of the security chain | Run it after the chain, where the authenticated identity is available; register it as a chain filter | A refusal has to cost less than the attempt it refuses, and an attempt that reached the chain has already paid for a bcrypt verification, which is the cost the credential-guessing ceiling exists to avoid.
