# CardDemo Migration Decision Log

This decision log satisfies the **Explainability rule** (Technical Specification §0.7.2 / §0.7.3). It is the authoritative record of every non-trivial decision made while migrating the **AWS CardDemo** application from its IBM z/OS **COBOL / CICS / VSAM / JCL / BMS** technology stack to a modern **Java 25 LTS + Spring Boot** application. The migration is performed **in the same repository**: the original COBOL, JCL, BMS, copybook, CSD, and data assets are retained **read-only under `legacy/`** for reference and traceability, and the new Java artifacts are, per the migration plan, to be created alongside them under `src/` (see the *Implementation status at this checkpoint* note immediately below).

> **Implementation status at this checkpoint.** This log is written at the **Legacy Oracle and Build Baseline** checkpoint. At this point the deliverables in place are: (a) the retained legacy assets under `legacy/` (COBOL programs, copybooks, BMS maps, symbolic map copybooks, JCL, PROC, CTL, CSD, catalog listing, and ASCII/EBCDIC data) that serve as the migration oracle, and (b) the Java **build baseline** — `pom.xml`, the Maven wrapper (`mvnw`, `mvnw.cmd`, `.mvn/wrapper/maven-wrapper.properties`), the JVM argument file `.mvn/jvm.config`, and these documentation deliverables. The Java **source tree** under `src/main/java`, `src/main/resources`, and `src/test/java` is **planned but not yet generated** at this checkpoint; every statement in this log that describes a Java class, package, entity, repository, service, controller, batch job, template, or test therefore describes a **planned** target artifact, not code that currently exists in the repository. Decisions are recorded now so that the subsequent generation phase implements them without re-litigation.

Per the Explainability rule, **rationale lives in this decision log, not in code comments.** Each row below captures a decision, the alternatives that were considered, the rationale, and the associated risks with their mitigations. Any deviation from a literal interpretation of the requirements is expected to have an explicit entry here; **a deviation that is not recorded in this log is treated as a defect.** Every decision preserves existing COBOL business behavior — no new business functionality is introduced (see the *No MQ / new external interfaces* entry and the *Suggested next tasks* section).

| **Maven 3.9.9** as the primary build tool, wrapper-pinned. | Gradle 8.x; a newer Maven patch (3.9.16); Maven 4.x. | Maven is chosen for reproducible builds via the committed Maven wrapper (`mvnw` / `mvnw.cmd` / `.mvn/wrapper/maven-wrapper.properties`) pinned to **3.9.9**, the version pinned by the frozen migration plan (§0.5.1) and provisioned in the build environment. Gradle 8.x remains a recorded alternative. |
| **Single Maven module** for the whole application. | Multi-module Maven layout. | A single module keeps the one-phase migration reviewable in one place while still preserving clean layer separation through packages. | Larger module. **Mitigation:** strict package boundaries — `config`, `domain`, `dto`, `repository`, `service`, `web`, `batch`, `exception`, `security`, `util`. Multi-module is recorded as an alternative. |
| **VSAM → one relational table per file**, preserving primary keys and alternate indexes. | A redesigned / denormalized relational schema. | One table per VSAM file with keys and alternate indexes preserved maximizes behavioral parity (e.g., `ACCOUNT-RECORD` `ACCT-ID PIC 9(11)` → `NUMERIC(11)` primary key; `CARDAIX` / `CXACAIX` / the transaction-by-card AIX → secondary indexes plus Spring Data derived queries). | Not an "ideal" normalized design. **Mitigation / accepted trade-off:** parity is prioritized over normalization — no denormalization or schema "improvements" are made. |
| **`java.math.BigDecimal`** for every monetary field, with a **per-statement `RoundingMode`** (`DOWN` where COBOL omits `ROUNDED`, `HALF_UP` where `ROUNDED` is present). | A single global rounding mode; floating-point (`double`/`float`) for money. | COBOL rounding is defined per-`COMPUTE`. A full audit of every arithmetic statement in the 28 legacy programs (see the **Monetary rounding inventory** subsection below) shows that **no `ROUNDED` clause is present anywhere in the codebase**, so — under the general rule — **every** monetary computation truncates and maps to `RoundingMode.DOWN`; the `HALF_UP` branch of the rule has zero instances here but is retained for correctness if future maintenance introduces a `ROUNDED` statement. The canonical case is `CBACT04C` `1300-COMPUTE-INTEREST`: `(TRAN-CAT-BAL * DIS-INT-RATE) / 1200` into `WS-MONTHLY-INT PIC S9(09)V99` with **no** `ROUNDED`, truncated to 2 decimals. Floating-point is prohibited for monetary values. | Requires a per-statement audit of every `COMPUTE` (completed — see inventory). **Mitigation:** each computation's rounding mode is recorded in the inventory below and will be parity-tested against the COBOL result, with the interest calculation carrying a dedicated parity-oracle test. |
| **`CHAR(n)`** for fixed-width `PIC X(n)` columns. | `VARCHAR` with application-level trimming. | `CHAR(n)` preserves the fixed-width, trailing-space semantics of `PIC X(n)`. | Trailing-space handling can affect string comparisons. **Mitigation:** consistent `CHAR` mapping plus a `FixedWidthRecordMapper` that preserves byte-exact layouts for flat-file feeds. |
| **Server-rendered Thymeleaf** screens for the web tier. | A REST/JSON API plus a single-page application (SPA). | Server-rendered screens reproduce the 3270/BMS field, label, length, color, and PF-key contract one-for-one on the 24×80 grid, and avoid introducing a **new** external interface (a public REST/JSON API would be feature expansion). | Less "modern" UI. **Mitigation / accepted trade-off:** the screen contract is preserved exactly and scope expansion is avoided. |
| **Preserve the cleartext password-comparison behavior** of signon, while **removing hardcoded credentials** in favor of externalized configuration. | Introduce BCrypt password hashing now. | Functional parity requires preserving `COSGN00C`'s cleartext comparison (`SEC-USR-PWD = WS-USER-PWD`) and its role routing (admin → `COADM01C`, user → `COMEN01C`). Changing the authentication algorithm would change observable behavior. | Cleartext authentication is insecure. **Mitigations:** no hardcoded secrets (credentials come from environment variables / the database only), and password hashing (BCrypt) is flagged as a *suggested next task* rather than silently changing authentication behavior. |
| **Preserve control flow and paragraph→method traceability** while using **idiomatic Spring layering**. | A pure idiomatic rewrite that discards paragraph structure; OR a mechanical 1:1 transliteration (the "Jobol" anti-pattern). | The prompt mandates paragraph preservation and 100% traceability, which is in tension with the "Jobol" anti-pattern. The tension is resolved by keeping each numbered COBOL paragraph as a method (traceable and control-flow-preserving) while still organizing code into idiomatic layers. | Some service methods mirror COBOL granularity. **Mitigation / accepted trade-off:** this granularity is accepted to guarantee 100% traceability and behavioral parity. |
| **Deterministic bytewise / ASCII collation** (PostgreSQL `C` / `POSIX`) — or an explicit `ORDER BY` on the `CHAR` key — wherever ordering is observable. | Rely on the default database collation. | EBCDIC and ASCII/UTF-8 sort orders differ; this matters where ordering is observable, notably `COMBTRAN`'s `SORT FIELDS=(TRAN-ID,A)`. Because keys are numeric or uppercase alphanumeric, a bytewise/ASCII collation reproduces the legacy ordering. | A collation mismatch could reorder output. **Mitigation:** parity tests validate ordering against the ASCII fixtures. |
| **Consolidate `CUSTREC.cpy` and `CVCUS01Y.cpy`** into a single `domain.Customer` entity. | Keep two separate customer types. | Both copybooks define the same `01 CUSTOMER-RECORD` CUSTDAT layout with the **same 500-byte physical record and byte-for-byte identical field offsets** (`CUST-ID 9(09)` at bytes 1–9, names `X(25)`, address lines `X(50)`, `CUST-SSN 9(09)`, `CUST-GOVT-ISSUED-ID X(20)`, …), so a single entity faithfully represents both. They are **not textually identical**, however: the 19th field (the date-of-birth field, `PIC X(10)` at bytes 309–318) is named **`CUST-DOB-YYYYMMDD` in `CUSTREC.cpy`** but **`CUST-DOB-YYYY-MM-DD` in `CVCUS01Y.cpy`**. This is a **data-name alias only** — same position, same length, same picture — so it does not affect the physical layout, and consolidation is safe. | An unnoticed layout difference could break parity. **Mitigations:** the two layouts were compared field-by-field and reconcile at every offset; the sole difference (the DOB data-name alias, verified on line 19 of each copybook) is recorded here and in the traceability matrix; the `domain.Customer` field is documented as carrying both source aliases. |
| **Do not migrate `UNUSED1Y.cpy`** (intentional non-migration — dead code). | Migrate it for completeness. | `UNUSED1Y.cpy` (`01 UNUSED-DATA`) is not referenced by any of the 28 COBOL programs; migrating it would introduce dead Java code. | None. **Mitigation:** the omission is recorded here (and in the traceability matrix) so it is explicit, not silently dropped. |
| **Do not create a standalone service for `COCRDSEC` / transaction `CDV1`** (intentional non-migration); realize it via `config/SecurityConfig.java`. | Create a standalone card-detail security service. | `COCRDSEC` is a CICS-only card-detail security variant defined in `CARDDEMO.CSD` (program `COCRDSEC`, transaction `CDV1`) with **no** `.cbl` business logic; its intent is authorization, expressed as Spring Security URL/method rules. | None. **Mitigation:** the authorization behavior is preserved through Spring Security; the mapping is recorded in the traceability matrix. |
| **Treat `OPENFIL.jcl` and `CLOSEFIL.jcl` as not applicable** (intentional non-migration — no target artifact). | Model them as batch steps. | These jobs enable/disable CICS files ("Open files in CICS" / "Close files in CICS"). Under a Spring-managed JDBC connection pool there is no equivalent operational step. | None. **Mitigation:** documented as N/A here and in the traceability matrix. |
| **Realize `CBADMCDJ.jcl` (the CICS `DFHCSDUP` CSD install) as a documented no-op `Tasklet`** in `batch/AdminBatchJobConfig.java`, retained for 1:1 traceability. | Omit the job entirely (no target artifact); or emulate `DFHCSDUP` CSD installation in Java. | `CBADMCDJ.jcl` ran the CICS utility `DFHCSDUP` to install CICS System Definition (CSD) resources — the `CARDDEMO` group of programs, transactions, and file/mapset definitions (e.g. `DEFINE PROGRAM(COSGN00C) … TRANSID(CC00)`). It carried **no business or data logic**. Under Spring Boot there is no CICS region and no CSD; those resource definitions are realized declaratively by `config/SecurityConfig` (URL/method routing plus `ROLE_ADMIN` / `ROLE_USER` authorities) and by the controller/service/repository bean wiring, so there is no runtime work for the job to perform. | **Introduce no new external interfaces** — specifically no MQ/JMS (and no Db2, IMS, FTP/SFTP, REST/SOAP). | Add MQ, following the prompt's mention of "MQ … interface contracts". | The source COBOL contains **no** MQ/JMS/Db2/IMS/FTP/SFTP/REST/SOAP interface — these are all on the unimplemented AWS CardDemo V2 roadmap. Parity means preserving what exists and adding nothing; adding MQ would be feature expansion. | Prompt ambiguity around "MQ … interface contracts". **Mitigation:** it is explicitly documented that no MQ exists in the source and that introducing it is out of scope for this migration. |
| **Treat Lombok and MapStruct as optional** aids, included only where actually used. | Hand-written boilerplate and hand-written copybook↔DTO mappers. | Lombok can reduce entity/DTO boilerplate and MapStruct can generate copybook↔DTO mappers; both are conveniences, not requirements. | Annotation processing can conflict with the zero-warning build. **Mitigation:** configure annotation-processor paths and include these libraries only if genuinely used. |
| **Preserve legacy handling of sensitive fields for parity, while applying non-behavioral controls.** | Change storage/masking/authentication now (hashing, tokenization, encryption at rest). | The migration must not alter observable behavior, so sensitive data keep their legacy representation: the signon password is compared in cleartext (`CSUSR01Y` `SEC-USR-PWD PIC X(08)` at bytes 49–56; compared at `COSGN00C` against `WS-USER-PWD`), and the full PAN, CVV, SSN, government-issued id, DOB, and monetary balances retain their exact fixed-width record positions in feeds and reports. The **classification and the applied controls** (which fields are sensitive; where each is stored, displayed, and logged) are enumerated in the traceability matrix's field-classification section. Controls that do **not** change behavior are applied now: **no hardcoded credentials** (datasource and any secrets come only from environment variables / the database), **no sensitive values written to logs** (structured logging excludes PAN/CVV/SSN/password), and **role/method authorization** (see the Spring Security row) gating the screens that expose sensitive data. | Retaining cleartext/plaintext-at-rest is insecure. **Mitigations:** the non-behavioral controls above are in force from the initial implementation; behavior-changing hardening — password hashing (BCrypt), PAN tokenization/masking beyond what the legacy screens already mask, and encryption at rest — is deferred and recorded under *Suggested next tasks* so it is explicit rather than silently omitted. |
| **Realize the "executable" copybooks as Java logic, not as passive constants/linkage.** | Treat every copybook as a pure data structure (constants/DTO only). | Three copybooks contain procedural content rather than only data: `CSUTLDPY` supplies **14 executable date-validation paragraphs** (performed inline by callers), `CSSTRPFY` supplies PF-key handling logic, and `CSSETATY` supplies executable `COPY … REPLACING` screen-attribute logic. Faithful parity requires porting their **behavior** (into `util.DateConversionSupport`/`util.PfKeyHandler` and the screen-attribute handling) — not merely emitting constant tables — otherwise validation and PF-key/attribute behavior would silently change. | Mischaracterizing them as constants would drop logic. **Mitigation:** the traceability matrix records each as executable and maps its paragraphs/replacing-logic to the concrete target methods; parity tests cover the date-validation outcomes. |

## Suggested next tasks (out of scope)

The following items are **not delivered in this migration** — they are recorded here (per §0.7.3 and the Onboarding rule) as recommended follow-up work that lies outside the "no feature expansion" scope of this deliverable:

- **Upgrade to Spring Boot 4.x** — addresses the Spring Boot 3.5 OSS end-of-life (2026-06-30) and the resulting gap in future CVE patches.
- **Introduce password hashing (BCrypt)** — replaces the preserved cleartext password comparison with a modern password-hashing scheme (a behavioral change, deliberately deferred to preserve parity in this migration).
- **Add a CI/CD pipeline under `.github/workflows/**`** — the repository currently has no CI pipeline; adding one is recommended but out of scope here.
