# Business Rule Flags

Every rule in the Common Business Oriented Language (COBOL) source that reads as ambiguous, undocumented or inconsistent is recorded below, with the file and line to open. The requirements asked for exactly this: *"Flag any business rule in the original COBOL that is ambiguous, undocumented, or inconsistent (CardDemo intentionally varies coding style across modules) rather than guessing — surface it in the tech spec for human review."* Nothing here was inferred from a summary; every locator was opened and read. Why a choice was made lives in the [decision log](decision-log.md), so the Handling column below states only what the platform does.

Transformation rule T7 governs that column: reproduce a source defect, flag it, and never correct it quietly. Parity with the source is the contract, which makes correcting any finding below a decision only the project owner can take. Nine rows do something other than reproduce and flag, and each is marked **declared deviation**, with its reasoning in the decision log.

## Register coverage

All 65 register items, in three blocks. **An identifier is a permanent contract, never reused and never renumbered.** [Equivalence results](equivalence-results.md), [suggested next tasks](suggested-next-tasks.md) and the [traceability matrix](traceability-matrix.md) cite findings by number, so a renumbering would silently repoint every one of those citations at a different finding.

Items **1 to 26** are the set the specification fixes, in the order it fixes them. Items **27 to 40** were appended in the order they were found, and an earlier revision of this document lost eleven of them by collapsing the register. Items **41 upward** were appended by the completeness review of the validation and date-handling members, in the order that review found them.

Within one cell, a bare line reference such as `:L34` belongs to the file named just before it.

## The largest item: a named program that does not exist

Item 1 is the largest entry in the register, because the requirements name the authorization path by program and transaction identifier and neither exists here. Two searches establish the absence: `COPAUA0C` matches no file and no line anywhere under `app/`, and `CP00` matches no line of `app/csd/CARDDEMO.CSD`. The 28 members of `app/cbl/` were listed and read; none of them is a renamed equivalent.

The authorization behaviour was therefore synthesised from three programs that do exist, and each contributes a different part:

- `app/cbl/CBTRN02C.cbl:L380-L420` supplies the four decline rules and their verbatim descriptions, which is the only validate-and-authorize logic in the repository.
- `app/cbl/COTRN02C.cbl` supplies the synchronous request contract: which fields a caller sends, and how each is validated.
- `app/cbl/COSGN00C.cbl:L223-L240` supplies the credential comparison and the administrator-versus-user fork.

**What the project owner should confirm:** that the batch validation path is the right ancestor for a synchronous authorization service, and that no authorization program exists outside this repository.

## Departures this platform makes from the source

The register records source behaviour. The four entries below record the opposite case: places where the platform answers differently from the source on purpose, and one place where it deliberately answers the same and a reviewer will want to know why. None is a defect in the source, so none belongs in the register, and all four are here because a reviewer checking parity will look for them here.

### D1. Card detail refuses a row that belongs to another account

The source reads a card by its number alone. Paragraph `9100-GETCARD-BYACCTCARD` at `app/cbl/COCRDSLC.cbl:L736` moves the card number into the record key at `:L740`. The statement above it, which would have moved the account identifier into the same key, is commented out at `:L739`. A signed-on user who typed any account identifier beside a real card number was shown that card.

The card service refuses that pairing and answers with the same absent-row message the source gives when its own not-found limb fires. Transformation rule T7 asks for a source defect to be reproduced and flagged, and this gap is not a source rule. The source reached that program only through the terminal signon at `app/cbl/COSGN00C.cbl`, which granted every user every card, so no per-card authority existed for the omission to weaken. The platform does grant one, which is why the account is checked.

**What the project owner should know:** a client sending a real card number beside the wrong account identifier now receives an absent-row answer where the source returned the card. No shipped request does this, because each of the 50 rows in `app/data/ASCII/carddata.txt` names one account.

### D2. Text bound for a cardholder is restricted to printable United States ASCII

The source places no character restriction on the text it renders. `app/cbl/CBSTM03A.CBL:L86-L159` lays each transaction across counted character positions of a print record and pads the remainder. Alignment is therefore a property of the layout rather than of a validation, and no paragraph refuses a value for the characters it holds.

The platform refuses one. A single pattern constrains every text component of the authorized and posted events. The same pattern constrains the free-text fields of the authorization, account and customer update requests. A synchronous caller sending a value outside it receives a validation refusal, and an event carrying one is dead-lettered rather than rendered out of column.

**What the project owner should decide:** whether refusing an accented merchant name or cardholder description is the intended behaviour, or whether a transliteration step should run ahead of rendering. No shipped fixture reaches the question, because every text value across the nine fixtures under `app/data/ASCII/` is already printable ASCII. [Suggested next tasks](suggested-next-tasks.md) carries the confirmation as a task.

### D3. A card expiry that names no day of the calendar is refused

The source stores one. `app/cbl/COCRDUPC.cbl:L1467-L1474` joins the submitted year, month and day with hyphens into `CARD-UPDATE-EXPIRAION-DATE`, which redefines `CARD-EXPIRAION-DATE PIC X(10)` at `app/cpy/CVACT02Y.cpy:L9`. Ten characters of text hold `2028-02-30` as readily as `2028-02-28`, and no paragraph checks which it is: the edit chain closes at `1260-EDIT-EXPIRY-YEAR-EXIT` at `app/cbl/COCRDUPC.cbl:L945` and `2000-DECIDE-ACTION` opens at `:L948`, with no paragraph between them reaching the day.

Column `expiration_date` is a `DATE`, which cannot hold a day that does not exist. Section 0.3.1 of the plan requires that type for this one field, because the field is positionally a calendar date and the source itself decomposes it into a year, a month and a day at `app/cbl/COCRDUPC.cbl:L117-L121`. So the platform refuses what the source would have stored, and it says so: `Card expiry year, month and day must name a day of the calendar`. The divergence is the column type's rather than a rule this platform added.

The rule reads the three values a caller submitted, which are the three the source writes. `app/cbl/COCRDUPC.cbl:L621` moves the day the screen sent into `CCUP-NEW-EXPDAY` and `:L1471` writes that same item into the record. The day never changed on a 3270 because `app/bms/COCRDUP.bms:L142` declares `EXPDAY` as `DRK`, `FSET` and `PROT` where the four other editable fields declare `UNPROT`, so an operator could not type into it and `app/cbl/COCRDUPC.cbl:L1110`, `:L1123` and `:L1127` sent the stored day back on every path. A request body has no protected field, so a caller can change the day and the column takes what it sends.

**What the project owner should decide:** whether refusing the impossible day is right, or whether the platform should store what the source stored. Storing it is not available at this column type, so the alternative is a `VARCHAR(10)` column and no rule, which would let `2028-02-30` reach a cardholder statement. No shipped fixture reaches the question: every one of the 50 rows in `app/data/ASCII/carddata.txt` carries a real date.

### D4. The card verification value is stored, and a security review asked for its removal

`CARD-CVV-CD PIC 9(03)` at `app/cpy/CVACT02Y.cpy:L7` is part of the card record, and `app/data/ASCII/carddata.txt` carries a value for all 50 rows. Column `card_verification_value CHAR(3) NOT NULL` in the card service holds it, and `V2__seed.sql` loads the fixture values into it. No application path reads the column: `CardEntity` exposes no accessor for the field, carries `@JsonIgnore` on it, prints the withheld marker in `toString`, and `applyUpdate` never changes it, matching `app/bms/COCRDUP.bms`, whose card update map declares no field for it. `card-updated-v1.json` and `card-updated-v2.json` declare no property for it and close their property sets, and the second carries an explicit `$comment` recording the absence. `CardholderDataExposureTest` asserts the field is unreachable through every one of those paths.

Sections 0.4.1 and 0.6.4 of the plan require exactly this arrangement. 0.6.4 states that the value "is persisted because the card record defines it and is never emitted", and 0.4.1 states that it "is stored but never serialized into any event or log". Section 0.2.2 places "payment-card industry controls beyond the single documented masking deviation" outside the engagement, so neither dropping the column nor encrypting it is work this plan authorises.

A security review of this platform recorded the storage as a critical finding and asked for the column, the mapping, the seed values and the preservation test to be removed through a forward migration. That change was not made, because the plan mandates the column and the plan is the agreed contract. The finding is recorded here rather than closed.

**What the project owner should decide:** whether card-record fidelity or non-retention of sensitive authentication data governs this column. Retaining a card verification value after authorization is prohibited by the payment-card industry data security standard, and no business path on this platform reads it, so the case for removal is strong and the only thing holding the column is the record layout. The removal is written up as a task in [suggested next tasks](suggested-next-tasks.md#remove-the-stored-card-verification-value). Until it is taken, the risk is exactly the one the decision log records: the value exists in the card service database, and a database, volume, snapshot or backup disclosure exposes it.
