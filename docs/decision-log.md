# CardDemo Modernization — Decision Log

This log records every non-trivial engineering decision, and every deviation from a literal reading of the requirements, taken while re-platforming the AWS CardDemo mainframe application (COBOL / CICS / VSAM / JCL / BMS on z/OS) to a cloud-native Java 21 / Spring Boot 4.1.0 microservices and React 19 stack. It is a first-class deliverable of the Explainability rule (AAP §0.7.2): rationale lives here, in this log, rather than in code comments. Each row names the decision, the alternatives that were weighed, the rationale, and the residual risk. Every deviation from a literal interpretation of the requirements has an explicit entry so the migration remains fully auditable.

**Legend.** Locators in square brackets — e.g. `[app/cbl/COSGN00C.cbl:L135-136]` — point to the authoritative legacy source (`path:line-range`) that grounds the decision. Legacy COBOL identifiers are quoted verbatim, including preserved source misspellings such as `ACCT-EXPIRAION-DATE`. Every table below uses the identical four columns — **Decision | Alternatives | Rationale | Risk** — as prescribed by AAP §0.7.3.

## 3. Security & Session

| Decision | Alternatives | Rationale | Risk |
|----------|--------------|-----------|------|

Where the legacy program has a literal for the condition (empty, non-numeric, bad format) it is used byte-exact; where the 3270 field width made over-length input *unrepresentable*, no legacy literal exists, so the message states the record-layout width instead of inventing a COBOL-looking sentence. | Framework protocol text is retained in `message` for protocol-level failures (malformed body, unsupported media type) | Replace it with a COBOL literal | No COBOL program has an analogue for "the HTTP body could not be parsed" — the 3270 datastream had no such failure mode. Substituting a business literal would misreport the cause; these messages are HTTP-level, not business output | A client sees framework wording for protocol errors; deliberately scoped to failures with no legacy analogue |

## 8. QA-Surfaced Batch, Runtime & Integration Deviations

Decisions taken while resolving the runtime findings raised by end-to-end QA of the integrated backend. Each is a choice a competent engineer could reasonably have made differently, so each is recorded here per the Explainability rule (AAP §0.7.2) rather than in code comments.

| Decision | Alternatives | Rationale | Risk |
|----------|--------------|-----------|------|
| The `BATCH_*` metadata schema is provisioned idempotently, by Flyway `V5__batch_metadata.sql` and a guarded application-side provisioner | Rely on `spring.batch.initialize-schema`; provision only by migration; provision only in code | The committed migration is column-for-column identical to `org/springframework/batch/core/schema-postgresql.sql` (6 tables, 3 sequences). Both paths use `CREATE ... IF NOT EXISTS` and the provisioner probes a sentinel table first, so a fresh database, a Flyway-managed database and a test container all converge on one schema without a "relation already exists" failure | Making the migration idempotent changed its checksum, which required one clean database rebuild |
| `run.id` is recorded as a NON-identifying job parameter for STATE-CHANGING runs only (see §11 for the repeatable read/print runs, where it is identifying) | Keep `run.id` identifying (a fresh UUID per launch) | An identifying `run.id` made every submission a brand-new `JobInstance`, so restart was impossible and a duplicate submission could never be detected. With it non-identifying, the business parameters alone establish job identity: an identical resubmission is refused with `JobInstanceAlreadyCompleteException`, and a failed instance is restartable. Idempotency is therefore a property of the business parameters, as the legacy operator-scheduled job streams assumed | Callers must vary a business parameter to run the same job stream twice for the same date |
| Every launcher supplies the job parameters its job requires, backed by configured defaults | Leave the parameter-less launchers passing empty `JobParameters` | Six launchers passed empty parameters to jobs whose beans late-bind `jobParameters['outputFile']` / `['inputFile']` / `['reportFile']`, so every run failed with "Batch file path must not be blank" while the launcher returned `STARTING` and the caller believed it had succeeded. Each launcher now resolves an effective file name (explicit argument, else a `carddemo.batch.*-file` default), validates it through the shared path resolver, and surfaces an acceptance failure synchronously | A default output name is shared across runs, so an unnamed relaunch overwrites the previous artefact |
| The daily-transaction feed is read with a streaming `JdbcCursorItemReader` over `daily_transactions`; `DailyTransaction` remains a non-entity value object | Promote `DailyTransaction` to a JPA `@Entity`; keep the hand-written in-memory repository | `TransactionPostingJob` read a hand-written `ConcurrentHashMap` that nothing populated, so every posting run reported `read=0 write=0` and finished COMPLETED while the persisted 300-row feed sat unread — a silent false success over financial data. `DailyTransaction` is deliberately a non-entity shared by services running `ddl-auto: validate`, so promoting it had an unacceptable blast radius; a cursor reader over an explicit 13-column projection ordered by `dalytran_id` preserves the `CBTRN02C` sequential read without touching the shared type | The reader is bound to the feed table's column names rather than to a mapped entity |
| A posting run that reads zero feed records FAILS with exit code `FAILED_EMPTY_FEED` and "Return code 12" | Let an empty feed complete successfully (`read=0`, RC 0) | An empty `DALYTRAN` feed is an operational fault, not a clean run: reporting success over it is exactly how the in-memory-repository defect stayed invisible. Failing loudly preserves the legacy 0/4/12 result-code contract, where 12 signals that the run must be investigated | A deliberately empty feed day now requires an operator acknowledgement |
| Online transaction ids are drawn from `transaction_id_seq` and probed with `existsById` before `saveAndFlush` | Reproduce the legacy browse-last-then-increment; trust the sequence alone; keep `save` | The sequence counts from one while the posting feed writes its own sixteen-digit ids, so a raw draw can name a row that already holds posted financial data — and JPA `save` MERGES an entity whose id exists, silently overwriting it and leaving the duplicate-id catch dead. The service now advances past any id already present (bounded at 1000 probes) and uses `saveAndFlush` so a concurrent claim surfaces inside the catch as the frozen `Tran ID already exist...` message. The observable sixteen-digit zero-padded wire format is unchanged | One `existsById` probe per assignment; a pathologically dense id space raises the frozen message rather than overwriting |
| The interest-calculation driving reader is `@StepScope` | Leave it a singleton; serialize interest runs with an external lock | The reader is an `ItemStream` holding the run's page cursor and peeked row. As a singleton it was shared by every concurrent step execution, so two simultaneous runs consumed one another's rows and each posted only part of the portfolio while both reported success. Step scoping gives each `StepExecution` its own reader, delegate, cursor and `ExecutionContext` entry | Concurrent runs over the same portfolio now contend on `accounts`; the loser is rejected by `@Version` optimistic locking and is restartable, which is the intended protection against double-posting interest |
| `BatchOutputPathResolver` was promoted to `carddemo-common` and every batch writer resolves through it, including the `dalyrejs.txt` reject file and `statements.txt` / `statements.html` | Duplicate the resolver per service; hard-code absolute container paths; relax the container filesystem | The resolver existed only in batch-service, so the statement writer defaulted to the working-directory-relative `output/statements.txt` and the reject writer to `dalyrejs.txt`. Both resolve under `/app` in the delivered containers, whose root filesystem is read-only, so statement generation could never succeed and every rejected record would have been lost. One shared resolver confines all batch I/O to a configured, writable, allowlisted root (defaulting under the JVM temporary directory) and rejects traversal outside it (CWE-22) | Absolute paths outside the configured root are refused by design, so callers and tests must supply root-relative names |
| A failed batch step deletes the output it was writing (`FailedOutputCleanupListener`) | Leave the partial file; write to a temporary file and rename atomically on success | A flat-file writer opens its resource when the step starts and closes it when the step ends whatever the outcome, so a failed dump left a file carrying BOTH legacy banners and zero data records — indistinguishable from a successful run over an empty input — and a failed statement run left two zero-byte files. Deleting on an unsuccessful step is the smallest change that guarantees no artefact survives to be mistaken for a completed run; temp-and-rename would have required reworking every writer's resource wiring. The listener is registered on EVERY file-producing step — `transactionPostingStep`, `accountReadStep`, `cardReadStep`, `cardXrefReadStep`, `customerReadStep`, `categoryBalanceReportStep`, `combineTransactionsStep`, `transactionDetailReportStep` and `statementGenerationStep` (both artefacts) — and resolves each path through the same `BatchOutputPathResolver` binding the writer uses, step-scoped wherever the destination is a job parameter. It had been registered on NO step at all, so this entry described behaviour that did not exist. Success is a `COMPLETED` status with an exit code BEGINNING with `COMPLETED`, so a posting run that ends `COMPLETED_WITH_REJECTS` keeps the reject generation that is its whole deliverable, while a business failure signalled through the exit code alone (`FAILED_EMPTY_FEED`) is still cleaned up. On the posting step the listener is registered BEFORE the reject-counting listener because `CompositeStepExecutionListener` runs `afterStep` in reverse registration order, so it observes the final status | A partially written file is discarded rather than retained for diagnosis; the failure cause remains in the step's exit message and the log |
| batch-service exposes a `/batch` launch surface, introduced together with its own `SecurityFilterChain` | Leave the job streams unreachable; expose the endpoints without an authorization boundary | The configured job streams — including the `CBTRN03C` / `TRANREPT` transaction-detail report — had no runtime entry point at all, so every request under `/batch` answered 404 even though the gateway already routed and role-gated `/batch/**`. The controller re-platforms the legacy operator submission through the CICS transient data queue `'JOBS'`. Adding endpoints to a service that declared no filter chain would have re-opened the very hole the downstream boundaries closed, so the boundary landed with the endpoints; job names are exposed verbatim as their bean names so the wire contract invents no identifiers | batch-service now participates in the shared Redis session, which its earlier "pure batch, no HTTP session" posture had excluded |
| A `CORPT00C` report request submits the transaction-detail report to batch-service through `BatchJobClient`, forwarding the caller's session | Keep launching the statement job; move `transactionDetailReportJob` into reporting-service; duplicate the job | AAP §0.4.4 maps `CORPT00C` + `TRANREPT.prc` to the transaction-detail report, but a report request launched `statementGenerationJob` instead, so the correct job had no caller. The job belongs to batch-service (AAP §0.4.4 `DataManagement*Job`), so relocating or duplicating it would contradict the mapping; a cross-service submission preserves ownership. The caller's `SESSION` cookie is forwarded so the launch is authorized as the signed-on user, which the shared Redis session makes meaningful in either service | A report request now depends on batch-service being reachable; that dependency is surfaced as the frozen submission-failure message rather than hidden |
| Job submission is synchronous while execution stays asynchronous; `@Async` was removed from the `@Configuration` launcher | Keep `@Async` and inspect the returned future; block the caller until the job finishes | The launcher was an `@Async` method on a `@Configuration` class returning a `CompletableFuture` that the caller discarded, so neither a refused submission nor a failed run could ever reach the user — a report request returned 200 while its job FAILED. Submission now completes on the calling thread (so a refusal raises the frozen `Unable to Write TDQ (JOBS)...`) while the accepted run proceeds on a bounded, correlation-propagating executor and its outcome is readable from the execution-status endpoint. Blocking the caller for the whole run would have breached the 200 ms online response target | Execution failure is observable by polling rather than in the submission response, matching the legacy submit-and-return semantics |
| `POST /reports/statements` is the entry point for the `CREASTMT` statement job stream | Leave statement generation reachable only from a report request | Re-pointing the report request at the transaction-detail report would otherwise have left the statement job stream with no caller. A dedicated endpoint keeps the two legacy paths distinct — `CORPT00C` submits the transaction report, `CREASTMT` generates statements — and accepts the two output names (`stmtFile`, `htmlFile`, the `STMTFILE`/`HTMLFILE` DD names) and nothing else: `CREASTMT` carries no `PARM`, so the endpoint no longer accepts a report type or a date window | An additional endpoint to secure; it is covered by the same session-based authorization as the report request |
| The launch executor is bounded (`setConcurrencyLimit(4)`) | Leave `SimpleAsyncTaskExecutor` unbounded | `SimpleAsyncTaskExecutor` pools no threads, so every submission spawned a fresh thread; a burst of launches could exhaust memory and saturate the JDBC pool. The legacy initiator ran a bounded number of concurrent job streams | A fifth concurrent submission queues rather than starting immediately |
| `JobInstance` creation uses `REPEATABLE_READ` isolation instead of Spring Batch's default `SERIALIZABLE` | Keep `SERIALIZABLE`; retry the launch on a transient serialization failure | PostgreSQL enforces `SERIALIZABLE` with Serializable Snapshot Isolation, which aborted one of two CONCURRENT launches — even for different job parameters — with "could not serialize access due to read/write dependencies among transactions", surfacing a raw SQL error instead of starting the job. `REPEATABLE_READ` removes that false conflict while the unique constraint on `BATCH_JOB_INSTANCE.JOB_KEY` remains the authoritative guard against a genuinely duplicated instance | Two launches racing on the SAME job key now surface a duplicate-key error instead of one blocking the other |
| Correlation ids are propagated into async and job threads by a shared `TaskDecorator`, and the launching thread's MDC is cleared afterwards | Accept empty `correlationId` on job-thread log lines; set the MDC only in the request filter | The shared web observability configuration was imported by nobody and four services had no correlation filter at all, so no log line carried a correlation id and a job's lines could not be tied back to the request that launched it. The decorator captures the id on the submitting thread and runs the task inside it; the launcher clears the id it seeded in a `finally` block so a pooled request thread cannot leak one submission's id onto an unrelated later request | The decorator must be applied to every executor that runs work on behalf of a request |
| Boot 4's modularized auto-configuration artefacts are declared explicitly (`spring-boot-session-data-redis`, `spring-boot-flyway`) | Rely on the technology artefact alone (`org.springframework.session:spring-session-data-redis`) | Spring Boot 4 moved auto-configuration into per-technology modules, so the session artefact alone leaves `spring.session.*` inert and never registers `SessionRepositoryFilter`; `HttpSession` then falls back to container-local storage. batch-service rejected every authenticated caller with 401 until the module was declared — diagnosed by diffing the fat jars against a working service | Every service adding a Boot-integrated technology must declare the matching `spring-boot-<tech>` module |
| `UserDetailsServiceAutoConfiguration` is excluded in all eight secured services | Leave it enabled; define a real in-memory `UserDetailsService` | These services authenticate from the shared CardDemo session, never from an in-memory user. Left enabled, Boot generates a random development credential and logs it at WARN on every start — both a usable in-memory account and an unrequested secret in the log. The exclusion was extended to the five downstream services and batch-service when the security starter was added to them | None; no service resolves a principal from an in-memory user |
| An unreachable routed upstream is reported as `503` with `Retry-After`, not `500` | Leave the default 500; add a circuit breaker with a fallback route | Routing raises `ResourceAccessException` when an upstream refuses the connection; unhandled it surfaced as 500, telling the caller the gateway itself is broken and is not retryable by convention, when the gateway is healthy and the condition is transient. A gateway-scoped handler ordered ahead of the shared handler maps it to 503 with the shared JSON error contract; the upstream host, port and exception detail are logged, never returned | A genuine gateway fault on a routed path is now reported as 503; a circuit breaker with per-route fallbacks remains a production follow-up |
| Generated batch artefacts and local run evidence are gitignored, with the legacy ASCII fixtures re-included explicitly | Leave the code's own default output names untracked-but-unignored | Every default output name in `JobSchedulingConfig`, `RejectFileItemWriter` and `StatementGenerationJob` is a runtime artefact that a job creates in the working directory, so any of them could be staged by accident. The patterns are copied from the constants that produce them — `acctdata-report*.txt`, `carddata-report*.txt`, `cardxref-report*.txt`, `custdata-report*.txt`, `tcatbal-report*.txt`, `tran-detail-report*.txt`, `combined-transactions*.txt`, `dalyrejs*.txt`, `statements.txt`, `statements.html`, `dailytran*.txt` — and each is ignored at any depth, together with the batch output root and the local evidence directory. An earlier revision of this entry claimed the same coverage while listing six INVENTED stems (`trandet*`, `catbal*`, `acctrept*`, `cardrept*`, `xrefrept*`, `custrept*`) that matched none of the names the code actually writes, so six of the eleven artefacts were not ignored at all; the patterns and this rationale were corrected together and every name re-verified with `git check-ignore -v`. Because the patterns match at any depth, `app/data/**` is re-included by negation so the committed `app/data/ASCII/dailytran.txt` seed fixture — which shares a name with the generated feed — stays trackable (verified: not ignored and tracked) | Deliberately committing a sample artefact under one of these names requires `git add -f` |
## 9. Schema Ownership, Runtime Configuration & Deployment Topology

Decisions taken while making the delivered stack actually run and actually be observable. Every row below was reached by reproducing a concrete runtime failure, so each records what was observed as well as what was chosen. These are the entries a reader needs in order to understand how the schema comes into existence, how the services find each other, how much of the database each one may consume, and how a request is traced and correlated end to end.

### 9.1 Database schema ownership and Flyway strategy

| Decision | Alternatives | Rationale | Risk |
|----------|--------------|-----------|------|
| ONE shared Flyway migration set, owned by `carddemo-common` at `classpath:db/migration`, applied by whichever service starts first | Per-service migrations owning only that service's tables (the original arrangement); or an external migration job with Flyway disabled in every service | Every one of the eight JPA services declares `@EntityScan("com.carddemo.common.domain")` with `ddl-auto: validate`, so EVERY service validates the FULL entity set at startup, not just "its own" tables. Per-service ownership therefore cannot work in any start order: a service that owns two tables still fails validation against the other nine. Consolidating the DDL and the seed data into one set that every service carries makes the schema complete no matter which container wins the race, and the Flyway history table makes the losers no-ops | Concurrent first starts contend on the history table; Flyway's own locking serialises them. Verified on a clean volume: all nine services come up healthy in a single `docker compose up` with no ordering constraint, and the schema contains all 11 business tables |
| `spring-boot-flyway` (the Boot 4 auto-configuration module) added as an explicit dependency to every JPA service | Rely on `flyway-core` alone, as the original poms did | Spring Boot 4 split auto-configuration out of the monolithic `spring-boot-autoconfigure` jar into per-technology modules. With only `flyway-core` on the classpath the `spring.flyway.*` properties parse but nothing acts on them, so migrations silently never ran — the direct cause of the crash-loop on a clean volume | A missing Boot 4 auto-configuration module fails SILENTLY rather than loudly; the same class of defect was found for tracing (§9.4) and for three property renames (§9.6) |
| `ddl-auto: validate` retained in every service | `update` or `create` | Validation makes a schema/entity divergence a startup failure instead of a silent runtime error, and it guarantees the migrations — not Hibernate — remain the single source of truth for the schema | Any entity change without a matching migration blocks startup, which is the intended behaviour |
| `baseline-on-migrate: false` retained | `true` | `true` would let a service silently adopt a partially-migrated database as its baseline and skip the DDL it needs. With a single shared set there is no legacy schema to baseline over | An existing database not created by these migrations must be migrated manually |
| Spring Batch metadata DDL shipped as `V5__batch_metadata.sql` in the shared set | Let Spring Batch initialise its own schema; or ship it in `batch-service` only | THREE services run Spring Batch jobs (`batch-service`, `transaction-service`, `reporting-service`), so batch-service-local DDL would impose a hidden start-order requirement on the other two. Boot 4.1 also removed the entire `spring.batch.jdbc.*` property group, so `initialize-schema` no longer exists as a lever | The DDL must track the Spring Batch major version; it is the canonical PostgreSQL script for Batch 6 |
| Reference and test seed data delivered as `V2__seed_reference_data.sql` and `V3__seed_test_data.sql` | Seed from the ASCII fixtures at runtime | AAP §0.4.5 specifies exactly 7 transaction types, 18 categories and 51 disclosure groups, derived from `app/data/ASCII/{trantype,trancatg,discgrp}.txt`; expressing them as migrations makes the counts deterministic and verifiable | Verified at runtime: `select count(*)` returns 7 / 18 / 51 on a clean volume |
| The reporting-service test profile keeps Flyway DISABLED and provisions only what each test asserts on | Enable the shared migration set for tests so the container matches production | `V3` seeds 50 customers, accounts, cards and cross-references. `StatementGenerationJobIT` deletes its way to a known state before seeding, and would have to delete around foreign keys owned by tables it does not assert on. Each IT instead registers exactly the schema it needs via `@DynamicPropertySource` | The test container's schema is narrower than production's; the deployed configuration is exercised by the clean-volume compose run instead |
| `ReportingServiceApplicationIT` uses its OWN Testcontainers database (`jdbc:tc:postgresql:18:///carddemo_reporting_appit`) | Share the one container the other IT uses | `ContainerDatabaseDriver` caches exactly one container per JDBC URL for the whole JVM (proved: a single "Creating container for image: postgres:18" line for the entire failsafe run). Both ITs apply the same create-only Spring Batch DDL, so sharing would make whichever Spring context started second fail on already-existing tables | One extra throwaway container per build, roughly 1.6 s to start |

### 9.2 Connection budget and session lifecycle

| Decision | Alternatives | Rationale | Risk |
|----------|--------------|-----------|------|
| Explicit HikariCP sizing per service — `maximum-pool-size` 8 and `minimum-idle` 2 for the seven online services, 12 and 1 for `batch-service`, `idle-timeout` 300 s, all env-overridable | Leave HikariCP at its defaults | HikariCP defaults to `maximumPoolSize` 10 AND `minimumIdle` equal to it, so eight services held 80 of PostgreSQL's 100 connections **while completely idle** and starting any two further containers was refused with "FATAL: sorry, too many clients already". Sizing for the AAP §0.7.1 target of 150 concurrent users needs far less: the whole deployment's ceiling is now 7×8+12 = 68 and its measured steady state is 15. `batch-service` gets the larger pool because its chunk-oriented jobs hold a connection per chunk transaction | Under-sizing would queue requests instead of failing fast; the bounded `connection-timeout` (3 s) makes that visible, and `hikaricp_connections_pending` / `_timeout_total` are on the dashboard. Measured after the change: 15 idle backends (7.5% of the limit) held steady across 12 consecutive samples, and four extra service replicas ran healthily at 28/200 |
| PostgreSQL `max_connections` raised from the image default 100 to 200, in compose and in `k8s/deployment-postgres.yaml` | Leave it at 100 | Even with bounded pools, 100 leaves no operational headroom for replicas, `psql` sessions and monitoring. 200 keeps the steady-state footprint under 10% of the limit and admits two replicas of every service | Shared memory scales with `max_connections`, so the Kubernetes postgres container's memory request/limit was raised 256Mi→512Mi and 512Mi→1Gi to match |
| A REST API creates NO HTTP session for an unauthenticated caller: `NullRequestCache` on both security chains, and controllers read the session with `getSession(false)` | Accept the default `HttpSessionRequestCache` and inject `HttpSession` as a controller parameter | Injecting `HttpSession` forces `request.getSession()`, which CREATES a session on every anonymous business call, and `HttpSessionRequestCache` saves a session on every denied request so the caller can be redirected after login — a redirect a REST API never performs. Together they minted a Redis key per request; QA counted 258. Controllers now read an existing session only, and write the COMMAREA context back only if one already exists | A caller who has not signed on gets no server-side state, which is correct. Measured after the change: a 150-request mixed anonymous/denied burst created ZERO new `carddemo:session:*` keys, while a genuine `POST /auth/signon` still creates exactly one and a nine-request authenticated workflow reuses one stable id |
| One session attribute key, `carddemoSessionContext`, shared by every service | Let each service choose its own attribute name | The `api-gateway` used a private `sessionContext` key while all eight services and `SessionContextAuthenticationFilter` used `carddemoSessionContext`, so the gateway read a phantom empty COMMAREA and wrote a second redundant copy into the shared Redis session on every menu request | Verified: `HKEYS` on a live session shows exactly one context field |

### 9.5 Batch execution and deployment topology

| Decision | Alternatives | Rationale | Risk |
|----------|--------------|-----------|------|
| `carddemo-common`'s `JdbcBatchConfiguration extends JdbcDefaultBatchConfiguration`, imported by the three batch-capable applications | Accept Spring Boot's default batch configuration; declare `@EnableBatchProcessing` + `@EnableJdbcJobRepository` per service; subclass `DefaultBatchConfiguration` per service | Spring Batch 6's `DefaultBatchConfiguration.jobRepository()` returns a `ResourcelessJobRepository` — entirely in memory — and Boot 4.1 inherits it. Every job ran and completed while `BATCH_JOB_INSTANCE` and `BATCH_JOB_EXECUTION` stayed EMPTY, every execution reported id 1, the status endpoint could never resolve an execution, duplicate-instance detection could not fire, and the restart-from-last-committed-chunk behaviour the readers advertise was silently unavailable. Extending a `DefaultBatchConfiguration` is the supported extension point: `BatchAutoConfiguration` is `@ConditionalOnMissingBean(DefaultBatchConfiguration.class)` and backs off cleanly. ONE shared definition is declared rather than one per service: the annotation route and a `DefaultBatchConfiguration` subclass both declare the same `jobRepository` and `jobOperator` beans, so combining them in a context would reject the duplicate definitions, and a single class also keeps the create-isolation level and the observation registry identical in all three services | Replacing Boot's batch auto-configuration wholesale means new Boot batch defaults are not inherited automatically. `getObservationRegistry()` is overridden so `spring_batch_*` metrics still reach the real registry, and `getIsolationLevelForCreate()` is relaxed to `READ_COMMITTED` because PostgreSQL's serializable-snapshot isolation aborted concurrent metadata writes. Verified: 16 executions persisted, all COMPLETED, ids surviving a container restart |
| `getIsolationLevelForCreate()` returns `READ_COMMITTED` instead of the Spring Batch default `SERIALIZABLE` | Keep `SERIALIZABLE`; or retry on `CannotAcquireLockException` | Spring Batch applies this isolation level to the transaction interceptor advising EVERY `JobRepository` method, not only `create*`. Under PostgreSQL's serializable-snapshot isolation the foreign-key check behind `INSERT INTO BATCH_STEP_EXECUTION_CONTEXT` performs a predicate read that conflicts with a concurrent `BATCH_STEP_EXECUTION` insert, so submitting the nine jobs together made one of them end FAILED on a metadata write while its own business step had done nothing wrong. Nothing is weakened: `BATCH_JOB_INSTANCE` carries the unique constraint `JOB_INST_UN (JOB_NAME, JOB_KEY)`, which rejects a duplicate instance at any isolation level, and every launch adds a unique identifying `run.id` so two submissions never compute the same job key | Two concurrent submissions of the identical job key would both attempt the insert and one would fail on the unique index rather than on a serialization conflict. Verified: 36 truly-parallel submissions → 36 COMPLETED, 0 FAILED, and no serialization error in the PostgreSQL log. Concurrent independent job streams is also what the legacy JES initiators did |
| `batch-service` exposes `GET /batch/jobs`, `POST /batch/jobs/{jobName}` (202) and `GET /batch/jobs/executions/{id}` | Add `@Scheduled` triggers; or leave the jobs launchable only from a test | Nothing in the service could reach the nine `launch*` methods, so they were dead code and the six Spring Batch dashboard panels could never show data. Verified: authenticated 200 / anonymous 401 on the catalogue, all nine jobs 202 → COMPLETED |
| Every job parameter is optional, defaulting to the value the legacy job stream hard-codes | Require the caller to supply a business date | `INTCALC.jcl` hard-codes `PARM='2022071800'` on its `EXEC` card and `TRANREPT` hard-codes `PARM-START-DATE,C'2022-01-01'` / `PARM-END-DATE,C'2022-07-06'` in its `SYMNAMES` control card. Those values belong to the migrated job stream, not to the caller, so a bare `POST` reproduces exactly the job the mainframe operator submitted; the data-set names default the same way | A default window that matches no rows produces an empty report, which is the same outcome the legacy job would produce `[app/jcl/INTCALC.jcl:L22; app/jcl/TRANREPT.jcl; app/proc/TRANREPT.prc:L41-42]` |
| `BatchOutputPathResolver` lives in `carddemo-common`, verifies its output root is WRITABLE at construction, and resolves every batch file name inside it | Let each writer open the path it is given | Three writers passed a bare or relative file name straight to `FileSystemResource`, which resolves against the working directory `/app` — on the read-only root filesystem — so statement generation failed the step with "No such file or directory" and the DALYREJS reject writer would have failed the same way. Resolving through a shared component also keeps the CWE-22 containment check in one place, and checking writability at construction turns a mid-job I/O failure into a startup failure that names the directory and the environment variable | A service whose configured root is not writable will not start. That is deliberate and was verified: pointing the root back at `/app/output` reproduces a fail-fast "Failed to prepare batch root directory: /app/output" instead of a job-time error. ### 10.1 Daily transaction posting (`CBTRN02C` / `POSTTRAN.jcl`)

| Decision | Alternatives | Rationale | Risk |
|----------|--------------|-----------|------|
| The seeded `transactions` history is re-keyed into a reserved `1 000 000 000`–`1 999 999 999` id window by adding 1 000 000 000 — the `HISTORY_TRAN_ID_OFFSET` documented in the migration header — to the feed id it derives from | Seed no history at all; seed the history from invented ids unrelated to the feed; delete the staged feed once the history exists | The seed derives the 300-row history as the posted image of the 300-row `DALYTRAN` feed, and `CBTRN02C` `2900-WRITE-TRANSACTION-FILE` moves `DALYTRAN-ID` straight into `TRAN-ID`, so history and feed sharing ids made the FIRST record of the very first posting run fail on `transactions_pkey` — the delivered seed could not post a single record. Offsetting keeps the history a recognizable image of the same merchant activity (`0000000943918566` → `0000001943918566`), keeps `TRAN-ID` a 16-character zero-padded numeric string (`PIC X(16)`), and leaves the staged feed byte-identical to `app/data/ASCII/dailytran.txt` so a posting run behaves exactly as `POSTTRAN.jcl` does | The history's ids are not the ids that posting the current feed would produce; they are deliberately a prior cycle's window, which is documented in the migration header |
| `transaction_id_seq`'s baseline is the maximum over BOTH `transactions` and the staged `daily_transactions` ids | Seed the sequence from `transactions` alone, as before | A feed record still waiting to post is an id already reserved in the transaction master, because posting writes it under its own `DALYTRAN-ID`. Ignoring it let the online add flow (`COTRN02C`) draw an id that the next posting run then tried to `WRITE` — the exact abend the reserved-id baseline exists to prevent | The online flow starts higher up the id space than the history alone implies |
| Every `daily_transactions` column `CBTRN02C` dereferences while validating is `NOT NULL`, with `CHECK (LENGTH(dalytran_orig_ts) >= 10)` | Leave the columns nullable and null-guard each dereference in the processor; give a malformed row a new reject code | `DALYTRAN` is a fixed-width 350-byte sequential data set: a record physically cannot be missing `DALYTRAN-AMT` or carry a five-character `DALYTRAN-ORIG-TS`, so such a row is not a `DALYTRAN` record and has no legacy analogue. Nullable columns let one reach `1500-VALIDATE-TRAN`, where it aborted the step with a raw `NullPointerException` / `StringIndexOutOfBoundsException` on every rerun, blocking every later record and producing no reject record at all. The constraint refuses it at ingestion, where the loader can still fix it | A loader that previously staged an incomplete row now fails at insert; `DALYTRAN-PROC-TS` stays nullable because `2000-POST-TRANSACTION` stamps it at posting time |
| A staged row that is nevertheless unusable is a FEED FAULT — `DailyTransactionFeedValidator.requireUsableRecord` raises a `CardDemoException` naming the record and the offending field — not a business rejection | Invent reject code `104`; reject the row silently with code `100` | Reject codes `100`–`103` are a closed set with fixed messages in `CBTRN02C` `1500-VALIDATE-TRAN`; inventing a code would put a value on the 430-byte `DALYREJS` contract that no legacy consumer knows, and reusing `100` would misreport a corrupt record as an unknown card. The legacy program has no path for a malformed fixed-width record either — it abends — so failing the run with an actionable cause is the faithful outcome | A single corrupt staged row stops the run; the message names the record id and column so the fault is fixable without reading a stack trace |
| `transactionPostingJob` is launchable through `POST /transactions/batch/jobs/{jobName}` (`PostingJobController` + `PostingJobLaunchConfig`), identified by a `postingDate` parameter defaulting to the current date, and scheduled by a Kubernetes `CronJob` at `0 2 * * *` | Leave the job reachable only from tests; schedule it with an external scheduler calling the database directly | The job existed with no production caller at all, so the delivered stack could not post a day's transactions by any supported means, while every other job stream had a launch surface. ### 10.2 Monthly interest calculation (`CBACT04C` / `INTCALC.jcl`)

| Decision | Alternatives | Rationale | Risk |
|----------|--------------|-----------|------|
| `computeMonthlyInterest` divides with `RoundingMode.DOWN` | Keep `RoundingMode.HALF_UP`; use `HALF_EVEN` | `COMPUTE WS-MONTHLY-INT = (TRAN-CAT-BAL * DIS-INT-RATE) / 1200` stores into `PIC S9(09)V99` with no `ROUNDED` phrase, and COBOL TRUNCATES toward zero on an unrounded `COMPUTE`. `HALF_UP` posted a different cent on every balance whose exact quotient lay at or above the half — e.g. 100.00 at 5.00% is 0.41666…, which truncates to **0.41** and rounded to 0.42 — so interest, the account balance and `tran_cat_bal` all diverged from the legacy figure. `DOWN` truncates toward zero for negative balances too, matching the COBOL sign behaviour (−100.00 at 5.00% → −0.41). Tests that asserted the `HALF_UP` values encoded the defect and were corrected to the legacy values. This decision was ALREADY recorded in §2 (`setScale(2, RoundingMode.DOWN)`, NOT `HALF_UP`); only the implementation diverged from it | A cent lower than commercial rounding on the affected balances; that is the legacy figure. AAP 0.6.1's prose is self-contradictory here — it names `setScale(2, RoundingMode.HALF_UP)` while describing it as reproducing "COBOL's fixed-scale truncation" — and is resolved toward truncation by the COBOL source (no `ROUNDED` phrase) and by the binding constraints AAP 0.7.1 and 0.7.6, which forbid altering COBOL rounding or calculation logic |

### 11.3 Error Semantics, Precision & Batch Submission

| Decision | Alternatives | Rationale | Risk |
