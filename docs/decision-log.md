# CardDemo Migration Decision Log

This decision log satisfies the **Explainability rule** (Technical Specification §0.7.2 / §0.7.3). It is the authoritative record of every non-trivial decision made while migrating the **AWS CardDemo** application from its IBM z/OS **COBOL / CICS / VSAM / JCL / BMS** technology stack to a modern **Java 25 LTS + Spring Boot** application. The migration is performed **in the same repository**: the original COBOL, JCL, BMS, copybook, CSD, and data assets are retained **read-only under `legacy/`** for reference and traceability, and the new Java artifacts are generated alongside them under `src/` (see the *Implementation status* note immediately below).

> **Implementation status.** The migration has generated the full layered application; every decision recorded below is realized in the code that exists now. The deliverables in place are: (a) the retained legacy assets under `legacy/` (COBOL programs, copybooks, BMS maps, symbolic map copybooks, JCL, PROC, CTL, CSD, catalog listing, and ASCII/EBCDIC data) that serve as the migration oracle; (b) the Java **build baseline** — `pom.xml`, the Maven wrapper (`mvnw`, `mvnw.cmd`, `.mvn/wrapper/maven-wrapper.properties`), the JVM argument file `.mvn/jvm.config`; (c) these documentation deliverables; and (d) the **complete Java application** under `src/main/java/com/aws/carddemo`: the ten domain entities (`Account`, `Card`, `CardXref`, `Customer`, `Transaction`, `UserSecurity`, `TransactionCategoryBalance`, `DisclosureGroup`, `TransactionType`, `TransactionCategory`) plus the `domain/enums` lookup; the DTO layer (`CardDemoContext`, `CardWorkArea`, `DailyTransaction`, `StatementTransaction`, `DateStruct`, the `dto/menu` options, the `dto/report` models, and the 17 `dto/screen` form types); the ten Spring Data **`repository`** interfaces (one per VSAM file); the 17 online **`service/online`** classes and the nine **`web/controller`** routes covering all 18 CICS transaction ids; the **business Spring Batch** job configurations (`PostTransactionJobConfig`, `InterestCalcJobConfig`, `StatementJobConfig`, and the account/card/xref/customer/transaction/report/category-balance/combine jobs) alongside the `AdminBatchJobConfig` no-op driver; the `config` beans (`DataSourceConfig`, `BatchConfig`, `ObservabilityConfig`, `WebConfig`, and **`SecurityConfig`**); the full `exception` hierarchy plus the `GlobalExceptionHandler` `@ControllerAdvice`; the `security` layer (`CardDemoUserDetails`, **`CardDemoUserDetailsService`**, `CardDemoAuthenticationProvider`); the `util` helpers (`DateConversionService`, `DateConversionSupport`, `PfKeyHandler`, `CobolDecimal`, `FixedWidthRecordMapper`, and `util/constants`); together with `src/main/resources/application.yml` and the **`application-dev.yml` / `application-test.yml`** profiles, `src/main/resources/logback-spring.xml`, the Thymeleaf **`templates/`** (17 screens), the Flyway migrations `V0__spring_batch_metadata.sql`, **`V1__schema.sql`**, **`V2__reference_data.sql`**, **`V3__indexes.sql`**, and **`V4__card_xref_unique_card_num.sql`**, and the **`src/test/java`** test suites (unit + Testcontainers integration + parity). All statements in this log describe code that exists now; decisions are recorded so the design intent behind that code is not re-litigated during continued development.

Per the Explainability rule, **rationale lives in this decision log, not in code comments.** Each row below captures a decision, the alternatives that were considered, the rationale, and the associated risks with their mitigations. Any deviation from a literal interpretation of the requirements is expected to have an explicit entry here; **a deviation that is not recorded in this log is treated as a defect.** Every decision preserves existing COBOL business behavior — no new business functionality is introduced (see the *No MQ / new external interfaces* entry and the *Suggested next tasks* section).

| **Override the BOM-managed Flyway version to `11.20.3` (a PostgreSQL-18–tested release)** so the target PostgreSQL 18.4 server produces no Flyway compatibility warning and the build/start logs are warning-free (#49). | (1) Accept the informational *"support has not been tested"* warning emitted by the parent-BOM Flyway `11.7.2` (the originally-chosen approach); (2) pin the database down to the 16/17 floor to avoid the warning; (3) wait for the Spring Boot 4.x upgrade to advance Flyway transitively; (4) suppress the specific Flyway logger. | The BOM-managed Flyway `11.7.2` (`flyway-core` + `flyway-database-postgresql`) encodes its highest *tested* PostgreSQL major as **17**, so on every startup — and once per Testcontainers boot — it logged, at `WARN` from `o.f.c.i.database.base.Database`: *"Flyway upgrade recommended: PostgreSQL 18.4 is newer than this version of Flyway and support has not been tested. The latest supported version of PostgreSQL is 17."* That single line dominated the non-warning-free logs (hundreds of occurrences across the test suite) and blocked the zero-warning-build gate (AAP §0.7.1). Staying on the Flyway **11.x** major line the BOM already uses keeps the change API-stable and low-risk. This reverses the originally-recorded "accept the warning" decision, which the zero-warning-build review finding (#49) superseded. | Drifting one dependency off the parent BOM could, in principle, diverge from the exact set Spring Boot 3.5.16 validated. **Mitigations:** the override stays within the same Flyway 11.x major/API line the BOM ships (11.7.2 → 11.20.3); the full unit + integration suite (Testcontainers `postgres:18-alpine`) passes on 11.20.3 and the `V0`→`V4` migrations were re-verified to apply cleanly and idempotently; the `C`/`POSIX` collation keeps ordering deterministic across PostgreSQL versions; and the artifacts are fetched over HTTPS from Maven Central with checksum verification. The Spring Boot 4.x upgrade follow-on (which addresses the 3.5 OSS EOL / OWASP-CVE risk) will later carry a BOM-managed Flyway forward, at which point this explicit override can be dropped. |
| **Maven 3.9.9** as the primary build tool, wrapper-pinned. | Gradle 8.x; a newer Maven patch (3.9.16); Maven 4.x. | Maven is chosen for reproducible builds via the committed Maven wrapper (`mvnw` / `mvnw.cmd` / `.mvn/wrapper/maven-wrapper.properties`) pinned to **3.9.9**, the version pinned by the frozen migration plan (§0.5.1) and provisioned in the build environment. Staying on the Maven 3.9.x line is the correct production choice because Maven 4.x has **not** reached GA — as of 2026-07-18 it is only at release-candidate stage (4.0.0-rc-5) and the Apache Maven project explicitly labels the 4.x line "NOT safe for production use." | **This is not a zero-risk choice; the risk is documented rather than dismissed.** (1) **Superseded patch:** although the 3.9.x *minor line* is still one of the two maintained Maven series, the pinned *patch* 3.9.9 is superseded — the current recommended 3.9.x patch is **3.9.16** as of 2026-07-18 — so 3.9.9 lacks the bug and security fixes shipped in 3.9.10–3.9.16. (2) **Java 25 runtime warning (now eliminated):** under the Java 25 toolchain, Maven 3.9.9's own bundled Guava (`guava-33.2.1-jre.jar`) calls `sun.misc.Unsafe::objectFieldOffset`, which the JDK reports as a terminal-deprecation warning by default; this originates inside Maven infrastructure (not project code) so it cannot be removed from `pom.xml`, but it **is** eliminated for every prescribed invocation by the `--sun-misc-unsafe-memory-access=allow` flag added to `.mvn/jvm.config` — see the dedicated *Maven-infrastructure native-access warning* row below. **Mitigations:** builds are reproducible and tamper-evident via the wrapper pin, HTTPS-only Maven Central access, the Maven-distribution **SHA-256 pin** (`distributionSha256Sum` in `.mvn/wrapper/maven-wrapper.properties`, verified against Apache's published SHA-512 for `apache-maven-3.9.9-bin.zip` and then computed over those authenticated bytes), and Maven's artifact checksum verification; the local `~/.m2` repository isolates resolved artifacts; and both the project launcher's and Maven's own JVM warnings are silenced via `.mvn/jvm.config` (`--enable-native-access=ALL-UNNAMED` and `--sun-misc-unsafe-memory-access=allow`). **Approved follow-on (suggested next task):** advance the wrapper pin to **3.9.16** (a drop-in patch upgrade on the same minor line) and re-evaluate Maven 4.x once it reaches GA. Gradle 8.x remains a recorded alternative. |
| **Single Maven module** for the whole application. | Multi-module Maven layout. | A single module keeps the one-phase migration reviewable in one place while still preserving clean layer separation through packages. | Larger module. **Mitigation:** strict package boundaries — `config`, `domain`, `dto`, `repository`, `service`, `web`, `batch`, `exception`, `security`, `util`. Multi-module is recorded as an alternative. |
| **VSAM → one relational table per file**, preserving primary keys and alternate indexes. | A redesigned / denormalized relational schema. | One table per VSAM file with keys and alternate indexes preserved maximizes behavioral parity (e.g., `ACCOUNT-RECORD` `ACCT-ID PIC 9(11)` → `NUMERIC(11)` primary key; `CARDAIX` / `CXACAIX` / the transaction-by-card AIX → secondary indexes plus Spring Data derived queries). | Not an "ideal" normalized design. **Mitigation / accepted trade-off:** parity is prioritized over normalization — no denormalization or schema "improvements" are made. |
| **`java.math.BigDecimal`** for every monetary field, with a **per-statement `RoundingMode`** (`DOWN` where COBOL omits `ROUNDED`, `HALF_UP` where `ROUNDED` is present). | A single global rounding mode; floating-point (`double`/`float`) for money. | COBOL rounding is defined per-`COMPUTE`. A full audit of every arithmetic statement in the 28 legacy programs (see the **Monetary rounding inventory** subsection below) shows that **no `ROUNDED` clause is present anywhere in the codebase**, so — under the general rule — **every** monetary computation truncates and maps to `RoundingMode.DOWN`; the `HALF_UP` branch of the rule has zero instances here but is retained for correctness if future maintenance introduces a `ROUNDED` statement. The canonical case is `CBACT04C` `1300-COMPUTE-INTEREST`: `(TRAN-CAT-BAL * DIS-INT-RATE) / 1200` into `WS-MONTHLY-INT PIC S9(09)V99` with **no** `ROUNDED`, truncated to 2 decimals. Floating-point is prohibited for monetary values. | Requires a per-statement audit of every `COMPUTE` (completed — see inventory). **Mitigation:** each computation's rounding mode is recorded in the inventory below and is parity-tested against the COBOL result, with the interest calculation carrying a dedicated parity-oracle test (`InterestCalcJobConfigTest`, which asserts the canonical `(1000.00 * 19.99)/1200` truncates DOWN to `16.65`, not `16.66`). |
| **`CHAR(n)`** for fixed-width `PIC X(n)` columns. | `VARCHAR` with application-level trimming. | `CHAR(n)` preserves the fixed-width, trailing-space semantics of `PIC X(n)`. | Trailing-space handling can affect string comparisons. **Mitigation:** consistent `CHAR` mapping plus a `FixedWidthRecordMapper` that preserves byte-exact layouts for flat-file feeds. |
| **Server-rendered Thymeleaf** screens for the web tier. | A REST/JSON API plus a single-page application (SPA). | Server-rendered screens reproduce the 3270/BMS field, label, length, color, and PF-key contract one-for-one on the 24×80 grid, and avoid introducing a **new** external interface (a public REST/JSON API would be feature expansion). | Less "modern" UI. **Mitigation / accepted trade-off:** the screen contract is preserved exactly and scope expansion is avoided. |
| **Preserve the cleartext password-comparison behavior** of signon, while **removing hardcoded credentials** in favor of externalized configuration. | Introduce BCrypt password hashing now. | Functional parity requires preserving `COSGN00C`'s cleartext comparison (`SEC-USR-PWD = WS-USER-PWD`) and its role routing (admin → `COADM01C`, user → `COMEN01C`). Changing the authentication algorithm would change observable behavior. | Cleartext authentication is insecure. **Mitigations:** no hardcoded secrets (credentials come from environment variables / the database only), and password hashing (BCrypt) is flagged as a *suggested next task* rather than silently changing authentication behavior. |
| **Preserve control flow and paragraph→method traceability** while using **idiomatic Spring layering**. | A pure idiomatic rewrite that discards paragraph structure; OR a mechanical 1:1 transliteration (the "Jobol" anti-pattern). | The prompt mandates paragraph preservation and 100% traceability, which is in tension with the "Jobol" anti-pattern. The tension is resolved by keeping each numbered COBOL paragraph as a method (traceable and control-flow-preserving) while still organizing code into idiomatic layers. | Some service methods mirror COBOL granularity. **Mitigation / accepted trade-off:** this granularity is accepted to guarantee 100% traceability and behavioral parity. |
| **Deterministic bytewise / ASCII collation** (PostgreSQL `C` / `POSIX`) — or an explicit `ORDER BY` on the `CHAR` key — wherever ordering is observable. | Rely on the default database collation. | EBCDIC and ASCII/UTF-8 sort orders differ; this matters where ordering is observable, notably `COMBTRAN`'s `SORT FIELDS=(TRAN-ID,A)`. Because keys are numeric or uppercase alphanumeric, a bytewise/ASCII collation reproduces the legacy ordering. | A collation mismatch could reorder output. **Mitigation:** parity tests validate ordering against the ASCII fixtures. |
| **Consolidate `CUSTREC.cpy` and `CVCUS01Y.cpy`** into a single `domain.Customer` entity. | Keep two separate customer types. | Both copybooks define the same `01 CUSTOMER-RECORD` CUSTDAT layout with the **same 500-byte physical record and byte-for-byte identical field offsets** (`CUST-ID 9(09)` at bytes 1–9, names `X(25)`, address lines `X(50)`, `CUST-SSN 9(09)`, `CUST-GOVT-ISSUED-ID X(20)`, …), so a single entity faithfully represents both. They are **not textually identical**, however: the 19th field (the date-of-birth field, `PIC X(10)` at bytes 309–318) is named **`CUST-DOB-YYYYMMDD` in `CUSTREC.cpy`** but **`CUST-DOB-YYYY-MM-DD` in `CVCUS01Y.cpy`**. This is a **data-name alias only** — same position, same length, same picture — so it does not affect the physical layout, and consolidation is safe. | An unnoticed layout difference could break parity. **Mitigations:** the two layouts were compared field-by-field and reconcile at every offset; the sole difference (the DOB data-name alias, verified on line 19 of each copybook) is recorded here and in the traceability matrix; the `domain.Customer` field is documented as carrying both source aliases. |

## Suggested next tasks (out of scope)

The following items are **not delivered in this migration** — they are recorded here (per §0.7.3 and the Onboarding rule) as recommended follow-up work that lies outside the "no feature expansion" scope of this deliverable:

- **Upgrade to Spring Boot 4.x (or procure commercial/extended 3.5 support) — a hard pre-production prerequisite, scoped out of *this* deliverable by AAP §0.7.3.** This addresses the Spring Boot 3.5 OSS end-of-life (2026-06-30) and the resulting gap in future CVE patches, and is the resolution path for review finding #52. Because the AAP fixes the framework at `3.5.16`, the upgrade is *out of scope here*, but — per the honesty statement in the Spring Boot decision row — documenting the EOL is **not** a substitute for vendor support: before any production deployment, either obtain supported commercial/extended maintenance for 3.5.16 **or** complete the 4.x upgrade and re-run every parity/security gate. A newer parent BOM would also carry a BOM-managed Flyway forward, at which point the explicit `flyway.version=11.20.3` override (added to keep the PostgreSQL 18 build warning-free — see the *Flyway version override* decision row) can be dropped in favor of the BOM-managed version.
- **Introduce password hashing (BCrypt)** — replaces the preserved cleartext password comparison with a modern password-hashing scheme (a behavioral change, deliberately deferred to preserve parity in this migration).
- **Field-level PII masking / full-fidelity record output for the customer read+print job** — `batch/CustomerLoadJobConfig` (translating `CBCUS01C`) currently logs only the non-sensitive `custId` per record (the redacted operational-log sink). Should a byte-for-byte parity report sink for `CUSTOMER-RECORD` ever be required, add it with explicit field-level masking of PII (`CUST-SSN`, `CUST-GOVT-ISSUED-ID`, `CUST-DOB-*`); deferred here because `READCUST.jcl` produces no output dataset and masking is out of the "no feature expansion" scope.
- **Add a CI/CD pipeline under `.github/workflows/**`** — the repository currently has no CI pipeline; adding one is recommended but out of scope here.
- **Vendor the executive-deck libraries locally for a fully offline deck** — the deck currently loads reveal.js, Mermaid, and Lucide from the jsDelivr CDN (pinned, SRI-verified, under a restrictive CSP; see the *executive deck CDN hardening* decision row). Bundling those three assets under `blitzy-deck/references/` (and pointing the CSP/`<script>`/`<link>` tags at `'self'`) would make the deck genuinely self-contained and CDN-outage-proof; deferred here to keep the AAP-specified CDN delivery model.
