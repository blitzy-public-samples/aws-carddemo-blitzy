# CardDemo Migration — Decision Log

> **Project:** AWS CardDemo Mainframe-to-Java Migration  
> **Stack:** COBOL/CICS/VSAM/JCL → Java 25 LTS + Spring Boot 3.5.x + PostgreSQL 16+  
> **Last updated:** 2026-03-17  

## Purpose

This document captures every non-trivial implementation decision made during the migration of the AWS CardDemo mainframe application from COBOL/CICS/VSAM/JCL to Java 25 + Spring Boot 3.5.x. Each entry explains what was decided, what alternatives were considered, why the chosen approach was selected, and what risks it carries.

This log is a **living document** maintained alongside the codebase. Any deviation from literal COBOL behavior or any architectural choice that could reasonably have gone a different way is recorded here. The goal is full transparency: a reader unfamiliar with the project should be able to understand *why* the migrated system is shaped the way it is.

## Guiding Principles

The decisions above are governed by five core principles that were applied consistently throughout the migration:

1. **100% Behavioral Parity** — No feature expansion, no feature omission. Every COBOL paragraph, every validation rule, every batch step, and every data transformation must produce identical results in Java for identical inputs. The only approved deviations are security improvements (DEC-003) and platform-inapplicable concepts (DEC-017).

2. **Security Improvement** — Where the original COBOL application has known security weaknesses (plaintext passwords, hardcoded credentials), the Java migration applies modern security standards (BCrypt hashing, externalized credentials via environment variables) without changing functional behavior. Every security deviation is explicitly documented.

3. **Standard Java Patterns** — Prefer Spring ecosystem conventions and well-established Java patterns over custom solutions. Spring Data JPA for data access, Spring Security for authorization, Spring Batch for batch processing, Flyway for migrations. This reduces maintenance burden and leverages community-tested code.

4. **Local Testability** — Every decision must be locally verifiable without requiring a mainframe runtime, CICS region, or VSAM subsystem. Testcontainers provides production-equivalent database behavior. All quality gates (compilation, tests, coverage, OWASP) execute via `./mvnw clean verify`.

5. **Traceability** — Every decision traces back to a specific COBOL source construct, copybook, or JCL job. The bidirectional traceability matrix (`docs/traceability-matrix.md`) maps 100% of COBOL paragraphs to Java methods. This decision log explains the *why* behind every non-trivial *what*.
