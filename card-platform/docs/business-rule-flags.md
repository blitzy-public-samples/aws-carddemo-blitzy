# Business Rule Flags

Every rule in the Common Business Oriented Language (COBOL) source that reads as ambiguous, undocumented or inconsistent is recorded below, with the file and line to open. The requirements asked for exactly this: *"Flag any business rule in the original COBOL that is ambiguous, undocumented, or inconsistent (CardDemo intentionally varies coding style across modules) rather than guessing — surface it in the tech spec for human review."* Nothing here was inferred from a summary; every locator was opened and read. Why a choice was made lives in the [decision log](decision-log.md), so the Handling column below states only what the platform does.

Transformation rule T7 governs that column: reproduce a source defect, flag it, and never correct it quietly. Parity with the source is the contract, which makes correcting any finding below a decision only the project owner can take. Eight rows do something other than reproduce and flag, and each is marked **declared deviation**, with its reasoning in the decision log.

## The largest item: a named program that does not exist

Item 1 is the largest entry in the register, because the requirements name the authorization path by program and transaction identifier and neither exists here. Two searches establish the absence: `COPAUA0C` matches no file and no line anywhere under `app/`, and `CP00` matches no line of `app/csd/CARDDEMO.CSD`. The 28 members of `app/cbl/` were listed and read; none of them is a renamed equivalent.

The authorization behaviour was therefore synthesised from three programs that do exist, and each contributes a different part:

- `app/cbl/CBTRN02C.cbl:L380-L420` supplies the four decline rules and their verbatim descriptions, which is the only validate-and-authorize logic in the repository.
- `app/cbl/COTRN02C.cbl` supplies the synchronous request contract: which fields a caller sends, and how each is validated.
- `app/cbl/COSGN00C.cbl:L223-L240` supplies the credential comparison and the administrator-versus-user fork.

**What the project owner should confirm:** that the batch validation path is the right ancestor for a synchronous authorization service, and that no authorization program exists outside this repository.

## Coding style varies between modules

The requirements warned about this, and the warning holds down to individual field names. In the timestamp redefinition at `app/cbl/CBTRN02C.cbl:L161-L167`, the separator fields `DB2-STREEP-1`, `DB2-STREEP-2` and `DB2-STREEP-3` are named in Dutch while every neighbour is named in English. Every entry above therefore carries a locator instead of a generalisation.

## Departures this platform makes from the source

The register records source behaviour. The two entries below record the opposite case: places where the platform answers differently from the source on purpose. Neither is a defect in the source, so neither belongs in the register, and both are here because a reviewer checking parity will look for them here.

### D1. Card detail refuses a row that belongs to another account

The source reads a card by its number alone. Paragraph `9100-GETCARD-BYACCTCARD` at `app/cbl/COCRDSLC.cbl:L736` moves the card number into the record key at `:L740`. The statement above it, which would have moved the account identifier into the same key, is commented out at `:L739`. A signed-on user who typed any account identifier beside a real card number was shown that card.

The card service refuses that pairing and answers with the same absent-row message the source gives when its own not-found limb fires. Transformation rule T7 asks for a source defect to be reproduced and flagged, and this gap is not a source rule. The source reached that program only through the terminal signon at `app/cbl/COSGN00C.cbl`, which granted every user every card, so no per-card authority existed for the omission to weaken. The platform does grant one, which is why the account is checked.

**What the project owner should know:** a client sending a real card number beside the wrong account identifier now receives an absent-row answer where the source returned the card. No shipped request does this, because each of the 50 rows in `app/data/ASCII/carddata.txt` names one account.

### D2. Text bound for a cardholder is restricted to printable United States ASCII

The source places no character restriction on the text it renders. `app/cbl/CBSTM03A.CBL:L86-L159` lays each transaction across counted character positions of a print record and pads the remainder. Alignment is therefore a property of the layout rather than of a validation, and no paragraph refuses a value for the characters it holds.

The platform refuses one. A single pattern constrains every text component of the authorized and posted events. The same pattern constrains the free-text fields of the authorization, account and customer update requests. A synchronous caller sending a value outside it receives a validation refusal, and an event carrying one is dead-lettered rather than rendered out of column.

**What the project owner should decide:** whether refusing an accented merchant name or cardholder description is the intended behaviour, or whether a transliteration step should run ahead of rendering. No shipped fixture reaches the question, because every text value across the nine fixtures under `app/data/ASCII/` is already printable ASCII. [Suggested next tasks](suggested-next-tasks.md) carries the confirmation as a task.
