# CS-02-002: Category balance SLA scenario

Parent epic: [CS-02 Category Balance View](../README.md)

## Source Story (verbatim)

> ### 1. Details/Requirements
>
> As a product owner, I want category balances measured at the planning baseline, so that the 1-second SLA is proven for this view.
>
> Trace: CARD_REQ_TBD · Data Layouts · CVTRA01Y · TRAN-CAT-BAL
>
> Directive: 1-second SLA
>
> Account-data access path: Yes
>
> External integration or SLA-bound: Yes
>
> Capability: one scenario definition measures `GET /v1/accounts/{accountId}/category-balances`, the request behind the category balance view (`Data Layouts · CVTRA01Y`), on the performance runner of CS-01-003, which sends every call through the JDK `java.net.http` client and adds no dependency. It runs against the Compose stack `tests/docker-compose.yml` (CS-01-001) at the planning baseline, over entitled synthetic accounts `10000000001`–`10000010000`, ten category balances each and 100,000 rows in all, generated by CS-09-007 at stack start, with tokens and account slices from the performance harness. `./gradlew :card-servicing-service:performanceTest` runs it beside the other three SLA scenarios, and CI runs that task as the Performance stage. Target path:
>
> - `tests/performance/src/main/java/com/example/cardservicing/performance/scenarios/CategoryBalancesScenario.java` (create):
>   - Scenario definition: a JUnit 5 test class in the performance source set of CS-01-003 whose test method builds the runner with `LoadRunner.fromSystemProperties()` and passes one `LoadRunner.Scenario` to `run`. The scenario name is `category-balances`, and the endpoint path template is `/v1/accounts/{accountId}/category-balances` with the optional `typeCode` query value each target fills.
>   - Virtual users: the runner's mapping, two per regular fixture identity, users 1 and 2 as `USER0001` with `fixture-token-user0001` through users 9 and 10 as `USER0005` with `fixture-token-user0005` (CS-12-001).
>   - Targets: regular identity n (1–5) gets one 100-entry list. Position i (i = 1–100) holds synthetic account 10000000001 + 2,000(n − 1) + 10 + 20(i − 1), written as 11 digits, so the 100 accounts are distinct, lie inside the identity's 2,000-account slice, and sit at offsets that the balance summary scenario (CS-01-005) never reads. Odd positions are unfiltered. Even position 2j carries `typeCode` `01`, `02` or `03` in turn, `01` for j = 1, `02` for j = 2, `03` for j = 3, `01` again for j = 4, and so on. For `USER0001` the list starts `10000000011`, `10000000031` with `typeCode` `01`, `10000000051`, `10000000071` with `02`, and ends `10000001971`, `10000001991` with `02`; for `USER0005` it starts `10000008011` and ends `10000009991` with `02`.
>   - Volume check: before any call to the service, the class reads `docker compose -f tests/docker-compose.yml logs fixture-loader` and checks the load-report entries of AC5.
>   - Content probes: before the measured calls, the class sends four requests for `10000002000`, the last account of `USER0001`'s slice and outside every target list, with `fixture-token-user0001`: unfiltered and with `typeCode` `01`, `02` and `03`. It parses each body with the Jackson parser Spring Boot already brings.
>   - Shape split: after `run`, the class pairs each call record of the run result with the target it was sent for, groups the records into the unfiltered and the filtered shape, and computes p50, p95 and p99 of each shape over its 200 responses with the nearest-rank `PercentileCalculator` of CS-01-003. It writes one line per shape to standard output and appends the same lines to the scenario's report file under `cardservicing.performance.report-dir` once the runner has written it.
>
>     SCOPE-QUESTION (Resolved): What ties each call record to the target it was sent for, when ten virtual users complete their calls concurrently? Each call record of the runner's result carries its user number, its call index and the target it was sent for (CS-01-003), so the class groups the records by target alone: a record whose target carries a `typeCode` value belongs to the filtered shape, and one whose target carries none to the unfiltered shape. The grouping reads neither completion order nor a record's position in the result, so the same run always yields the same two groups. Each group must hold exactly 500 records, all with status 200, and any other count fails the scenario before the per-shape percentiles are computed.
>
>   - Stub conditions: the scenario declares the runner's no-timeout-retry condition on `cardservicing.carddata.v1.CardDataService/ListCategoryBalances`, `cardservicing.auth.v1.AuthService/ValidateToken` and `cardservicing.auth.v1.AuthService/AuthorizeAccountAccess`, each of which has entries in every run window.
>   - Completion log: the class reads `docker compose -f tests/docker-compose.yml logs card-servicing-service` just before and just after the runner's `run`, waiting up to 5 s for the last lines, and checks the completion lines added in between.
>   - Denial check: after the measured window, each regular identity sends one request for a sample account outside its entitlements through the class's own JDK `java.net.http.HttpClient` to the `cardservicing.performance.service-url` address. The class reads the highest `sequence` of the Card Data and Reference Data stub request logs (`GET /internal/stub/request-log`, CS-11-002) on the `cardservicing.performance.stub.card-data` and `cardservicing.performance.stub.reference-data` addresses before and after those five requests.
>   - Every `docker compose` command of this scenario runs through the JDK process API with the repository root as its working directory, and a non-zero exit fails the scenario. No token value appears in any assertion message or exception text.
> - Together this is the 1 file touched.
>
> In scope:
>
> - The scenario definition, its target lists and its account sets.
> - Its call mix of unfiltered and filtered calls.
> - Its volume check and content probes before the measured calls.
> - Its denial calls outside the measured set.
> - Its pass conditions on percentiles, status codes, data status, `cutoffMs` and retries.
>
> Not in this story:
>
> - The runner, the percentile computation and the report writer (CS-01-003).
> - The Compose stack (CS-01-001) and volume generation (CS-09-007).
> - Endpoint behaviour: validation, filter, ordering and degradation (CS-06-001, CS-06-002, CS-06-003).
> - Injected-failure cases (CS-06-002 and the integration suites).
> - The end-to-end step (CS-02-001).

> ### 2. Acceptance Criteria
>
> - AC1: The scenario runs the runner's load shape, 10 concurrent virtual users × 100 sequential calls, 1,000 calls in all, to `GET /v1/accounts/{accountId}/category-balances`, two users per regular identity `USER0001`–`USER0005` with their fixture tokens. Each user walks its identity's 100-entry target list once, in order, and the runner's entitlement check confirms before the first request that every target lies inside the identity's synthetic slice, for `USER0001` `10000000001`–`10000002000`. The Compose defaults `STUB_LATENCY_MS=0` and `STUB_FAILURE_RATE=0` apply on every stub and the scenario sets no per-stub override, so failure injection is off.
> - AC2: Every second call per user carries a `typeCode` filter that the synthetic-volume shape gives that account, `01`, `02` or `03` in turn, and the other calls are unfiltered: each user sends 50 unfiltered calls and 50 filtered calls, 17 on `01`, 17 on `02` and 16 on `03`. Before the measured calls, the content probes for `10000002000` return 200 with `X-Data-Status` `FRESH` and these `categoryBalances`: unfiltered, ten balances `200.01`–`200.10`; `typeCode` `01`, five balances `200.01`–`200.05`; `02`, three balances `200.06`–`200.08`; `03`, two balances `200.09` and `200.10`, each filtered balance carrying the requested `typeCode`. Any other answer fails the scenario before the measured calls start.
> - AC3: p50, p95 and p99, computed over successful requests, are each below 1,000 ms for the combined 1,000 calls, which the runner computes and enforces, and for each shape, the 500 unfiltered calls and the 500 filtered calls, which the class computes after the shape split. A percentile at 1,000 ms or above in any of the three sets fails the scenario.
> - AC4: Zero non-200 responses occur among the 1,000 calls. Any other status, or a call that reaches the runner's 5,000 ms request timeout, fails the scenario with a message naming the status and the request path, and `./gradlew :card-servicing-service:performanceTest` exits non-zero.
> - AC5: Before measurement starts, the fixture load report in the `fixture-loader` log shows the entries `category_balance` 50 loaded / 0 skipped and `synthetic_category_balance` 100,000 loaded / 0 skipped, 100,050 category balances in all, of which 100,000 are synthetic. A different count, a missing entry or a failed log read fails the scenario before the first request to the service.
> - AC6: Authorization, run outside the percentile set: after the measured window, one request per regular fixture identity for a sample account outside its entitlements, `USER0001` → `00000000011`, `USER0002` → `00000000021`, `USER0003` → `00000000031`, `USER0004` → `00000000041` and `USER0005` → `00000000001`, each returns 403 with error `code` `PERMISSION_DENIED` and a non-empty `traceId`. The highest `sequence` of the Card Data and Reference Data stub request logs is the same before the five requests and after them, so no account data is read from upstream before access is allowed; that no cache read precedes the access decision either is proven by the guard ordering of CS-12-003. Any other status, any other `code` or any new Card Data or Reference Data entry fails the scenario.
> - AC7: Timeout and deadline: every one of the 1,000 completion log lines added during the runner's `run` shows `cutoffMs` ≤ 900 (`REQUEST_DEADLINE_MS`). Each upstream attempt is bounded by the lesser of the 300 ms per-attempt timeout (`UPSTREAM_TIMEOUT_MS`) and the remaining budget, so any `ListCategoryBalances`, `ValidateToken` or `AuthorizeAccountAccess` entry in the scenario window with outcome `CANCELLED` or `DEADLINE_EXCEEDED`, or with a duration of 300 ms or more, fails the scenario through the runner's no-timeout-retry condition.
> - AC8: Retry: the result's stub figures show a retry count of 0 for every stub operation with entries in the scenario window, and `ValidateToken` and `AuthorizeAccountAccess` each show at least 1,000 calls, one per measured call. The retry rule, at most two retries (`UPSTREAM_MAX_RETRIES`), 50 ms then 100 ms backoff, on `UNAVAILABLE` or `DEADLINE_EXCEEDED` only, each retry starting only when its backoff plus a full 300 ms attempt fits before the 900 ms cut-off, is proven under injection by CS-06-002 and the integration suites CS-09-006, CS-11-007, CS-12-005 and CS-13-004.
> - AC9: Degradation: every measured 200 carries `X-Data-Status` `FRESH`, so the report counts 1,000 `FRESH`, 0 `STALE` and 0 `PARTIAL`, and a `STALE` or `PARTIAL` response fails the scenario. The degrade and fail-hard outcomes, excluded from the percentiles, are proven under injection by CS-06-002 and the integration suites of AC8, each with a logged `cutoffMs` ≤ 900 and a client-measured response below 1,000 ms: Auth fails closed with 401, 503 or 504; the category-balance read serves `STALE` from a cache entry within its 300 s max stale age, otherwise 503 or 504; an unusable transaction category list gives 200 `PARTIAL` with `typeDescription` and `categoryDescription` JSON `null`, and an unusable transaction type list gives 200 `PARTIAL` with `typeDescription` JSON `null`; a Config failure leaves the request and its `dataStatus` unchanged.
> - AC10: The report, in the task output and in `card-servicing-service/build/reports/performance/category-balances.txt`, lists the successful-request count and p50, p95 and p99 for each call shape: the runner's lines for the combined set, and the class's appended lines for the unfiltered and the filtered shape, each showing 500 successful requests. Latencies are printed in milliseconds with three decimals.

## Implementation Design

Recommended: Design Option A — each virtual user alternates unfiltered and type-filtered calls.

Rationale: one run of a thousand calls on the unchanged shared runner proves the one-second threshold for both request shapes of the category balance view.

- Rejected: Design Option B, unfiltered calls only, leaving the type-filtered shape unmeasured.

### Shared by both options

- Topology: the shared runner reaches the Compose stack's service, five stubs, store and cache through published ports.
- Naming: the scenario, its output lines and report carry the view's name.
- Addressing: each call names one account in its path, and the build supplies the service and stub log addresses.
- Isolation: measured calls read only the caller's synthetic slice, at offsets no other scenario reads, and denial calls name sample accounts outside the caller's range, so the end-to-end flow's accounts are never read.
- Fallback: none, so any failed status, precheck or threshold fails the run.
- Provisioning: the loader generates the synthetic volume before the stack reports ready.
- Cut-over: the swap changes only addresses and credentials, so the scenario reruns unchanged while real entitlements match the fixture ranges.
- Failures: injection stays off, as the category balance retrieval story and integration suites prove injected failures.

### Design Option A — alternated call shapes

Each regular identity gets a hundred distinct accounts from its synthetic slice, every second one narrowed to the first, second or third transaction type in turn. Both of its virtual users walk that list once in order, and the scenario holds each shape to the runner's threshold.

How it behaves:

- Unfiltered calls return ten balances, filtered calls the five, three or two of their type.
- Each account is cold until its first read fills its cache entry.
- Type and category descriptions are cached after first read.
- Four content probes on an unlisted account first confirm each shape's balance count.
- The loader log confirms the volume first, and completion and stub logs give deadline and retry evidence.
- Each call record's target, not completion order, sets its shape.
- One denial call per identity follows the measured window.

| No. | Decision (vs rejected) | Pro | Con |
|---|---|---|---|
| 1 | Alternated shapes (vs unfiltered calls only) | both shapes are measured | each shape gets half the calls |
| 2 | Per-shape and combined percentiles (vs combined only) | a slow shape shows alone | two more report lines |
| 3 | Synthetic accounts only (vs sample accounts too) | reads run at planning volume | the run needs generated volume |
| 4 | Offsets no other scenario reads (vs each slice's first hundred) | no other scenario warms them | the list needs a stride rule |
| 5 | Three types in turn (vs one type) | every filter selectivity is measured | each type gets a third of filtered calls |
| 6 | Denial calls after the window (vs inside the load) | percentiles stay over successful requests | extra calls follow measurement |

Effort and risk: small, one file, with shared-host runner capacity the main risk to per-shape percentiles.

### Design Option B — unfiltered calls only

Each regular identity requests Option A's hundred accounts unfiltered. The runner judges the one shape, and every other check matches Option A except that the content probe reads only the full list.

How it differs:

- Every call returns all ten balances.
- Its one shape rests on a thousand calls.

| No. | Decision (vs rejected) | Pro | Con |
|---|---|---|---|
| 1 | Unfiltered calls only (vs alternated shapes) | every call measures the full list | the filtered shape goes unmeasured |
| 2 | Combined percentiles only (vs per shape and combined) | the report keeps the runner's lines | a slow filtered shape stays hidden |

Effort and risk: smaller, one file, breaking the filtered-shape criteria.

### Recommendation

- Option: Design Option A.
- Why: it measures both shapes the view sends, in one file.
- Strongest argument against: each shape rests on five hundred of the thousand calls.
- Shared items that do not decide the choice: the runner, load shape, stride rule, volume and log checks, denial calls and thresholds.
- Flip conditions: the interface never sends the type filter.

## Design Validation

### Option A

Settled assumptions:

- The category balance volume story gives each synthetic account ten balances, split five, three and two over the first three types.
- Each identity's two-thousand-account slice holds every listed account, which no other scenario reads.
- The service applies the type filter to one account-wide cache entry.
- Failure injection is off, and the volume loads before the stack reports ready.
- The shared runner holds the load shape, combined percentiles, thresholds and report.
- Each call record names the user, call position and target.

Open assumptions:

- Runner capacity on the shared continuous integration host Open → repeated runs there compared with one idle-machine run.

| AC | Verdict | Why |
|---|---|---|
| AC1 | Holds | each list holds a hundred distinct slice accounts |
| AC2 | Holds | every second entry names a type each account holds |
| AC3 | Conditional | shared-host capacity is unproven until the first run |
| AC4 | Holds | with injection off every upstream read succeeds |
| AC5 | Holds | the loader log reports each entity's load |
| AC6 | Holds | the guard denies before any card or reference data read |
| AC7 | Holds | success-path stub calls end well inside the per-attempt limit |
| AC8 | Holds | attempts that never fail trigger no retry |
| AC9 | Holds | fresh reads and cached descriptions give the fresh status |
| AC10 | Holds | each record's target picks its shape line |
